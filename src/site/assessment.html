Cloud Health Office Platform Assessment

A capability assessment of the Cloud Health Office platform — September 2026

How to read this page. Every capability below is labelled Available today or On the roadmap. "Available today" means the code exists, is exercised by tests or by the published benchmark, and can be inspected in the public repository. "On the roadmap" means designed, partially built, or deliberately left as engagement work — not shipping.

Where this page and POSITIONING.md differ, POSITIONING.md is the source of truth. Where either differs from the code, the code is.

Executive Summary

Cloud Health Office is a source-available, Kubernetes-native claims administration platform for healthcare payers. It is built around a working adjudication pipeline — not a roadmap for one — and it publishes reproducible benchmark evidence for that pipeline against a one-million-claim corpus.

What makes it worth evaluating is narrow and specific: the adjudication path is real and staged, the calculation engines behind it are substantial code rather than wrappers, the CMS-0057-F FHIR surfaces are implemented, and the whole thing can be re-run from a clean clone by someone who does not work here.

What it is not, today: there is no production reference customer, no uptime SLA, no security certification, and no shipped connector to a legacy core administration system. Those are stated plainly below rather than left for you to discover.

Product Line Context

Cloud Health Office is a four-product-line portfolio, not a single product. Customers enter at any line and expand.

  • Public Tools — free utilities (fee schedule lookup, free-tier claims repricing).
  • Transactional Services — per-call APIs (Claims Repricing, Pricing API).
  • Managed Data Services — subscriptions for data that changes constantly (state Medicaid compliance updates, CMS fee schedule updates, provider verification, terminology).
  • Platform Engagement — payer-scale relationships priced per member per month, across three layers: Layer 1 — Compliance Accelerator, Layer 2 — Progressive Modernization, Layer 3 — Full CAPS Platform.

Available Today

Claims adjudication pipeline

A staged, event-driven adjudication orchestrator running eight registered stages: structural scrubbing, provider integrity, network and credentialing, benefit calculation, NCCI/MUE edits, coordination of benefits, AI examination, and persistence. Each stage can short-circuit, the pipeline is idempotent and tenant-pinned, and degraded-mode handling is explicit rather than implicit.

This is the path the Million Claim Challenge exercises end to end.

Adjudication engines

The engines are first-class code, unit-tested, and invoked by the pipeline rather than sitting beside it:

  • Benefit Engine — cost share, accumulators, plan resolution.
  • NCCI/MUE Engine — procedure-to-procedure and medically-unlikely edits, with per-tenant enforcement modes (pend, deny, soft validation).
  • Claims Scrub Engine — structural validation with 277CA-aligned rejects.
  • Fee Schedule Engine — Medicare RBRVS, OPPS APC, and MS-DRG pricing.
  • Coordination of Benefits Engine — primary-payer adjudication and secondary detection.
  • Prior Auth Rule Engine, Risk Adjustment Engine, Encounter Engine, Provider Verification Engine.

X12 transaction intake

Real tokenizer, parser and mapper implementations — not schema validation alone:

  • 837P / 837I / 837D — professional, institutional and dental claims.
  • 834 — enrollment, with plan-code mapping.
  • 270 / 271 — eligibility request and response.

835 (remittance advice) is generated today — real X12 005010X221A1 ERA output with BPR, CLP and SVC segment construction, single and batch. Inbound 835 parsing is not implemented; remittance that arrives from a clearinghouse is consumed through the gateway integration in normalised form rather than parsed from raw X12 here.

X12 276/277 (claim status) and 278 (prior authorization) are on the roadmap as X12 transactions. Prior authorization is available today through FHIR PAS instead — see below.

FHIR R4 and CMS-0057-F surfaces

Implemented API surfaces with SMART-on-FHIR scope enforcement: Prior Authorization Support (PAS), Coverage Requirements Discovery (CRD), Documentation Templates and Rules (DTR), Bulk Export, Patient Access, Provider Directory, and Payer-to-Payer exchange.

These are technical readiness surfaces. Production compliance additionally requires your source-system integration, configuration, and your own legal and compliance review. We do not claim certified compliance — see Regulatory posture.

AI claims examiner (advisory)

A real asynchronous pipeline: claims pended for NCCI modifier review publish to Kafka, a typed model client produces a recommendation, and an advisory result is written back. Default mode is advisory only, with no payment effect. It is decision support, not autonomous adjudication.

Operator portal

A Blazor operations console covering claims search and detail, mass adjudication run summaries with claim-level drilldown, work queues, eligibility and enrollment, authorizations, provider and member views, and benefit plans. Lifecycle timing, payment evidence and unsupported-scenario filters are inspectable per run.

Payments and revenue cycle

Capitation, premium billing, accounts receivable and payment services, including Stripe Connect disbursement and NACHA credit file generation. These are implemented services with test coverage, not integration placeholders.

Benchmark Evidence: The Million Claim Challenge

The Million Claim Challenge is the platform's proof ladder. It is deliberately not just a throughput test — it separates paid claims, business denials, expected pends, unexpected pends, platform failures, scoreable workflow matches and mismatches, unsupported scenarios, and payment deltas, and it reports each independently.

Correctness baseline — full 1,000,000-claim corpus (episode 15, run 2)

MeasureResult

Processed1,000,000
Platform failures0
Workflow checks matched129,981 / 130,000 (19 mismatched, 0 unsupported, 0 observation timeouts)

Highest sustained throughput at 1M claims (episode 16), same corpus

MeasureResult
Throughput155.89 claims/sec (P95 910 ms, P99 1,205 ms)
Workflow checks matched129,980 / 130,000
Payment gate19,982 / 19,982 exact within $0.01
Observation timeouts122 — claims that became terminal after the validator's 180-second window

Those 122 are an observation deadline, not lost claims: post-run verification found all 1,000,000 claims terminal, 2,000,000 lifecycle events, zero dead letters and zero pod restarts. Because they left 20 workflow checks unreconciled inside the run artifact, episode 15 — not 16 — is cited as the strict zero-failure baseline.

Environment, stated plainly. These are local Docker Desktop Kubernetes runs on a developer workstation. They are engineering benchmarks, not production cloud capacity claims. Correctness gates are seed-reproducible; throughput figures are hardware-dependent and will not reproduce exactly elsewhere. The platform has not been run against a top-tier payer's production volume.

Every published run carries its commit SHA, seed, exact command line, environment description and raw validator output, so the result can be audited rather than taken on trust. The generator, validator and runner are all in the repository.

On the Roadmap

Stated here because a capability assessment that only lists strengths is a brochure.

Core administration system adapters — engagement work by design

Adapter interfaces for Facets, QNXT and HealthEdge are defined and stable. No vendor connector ships in the box, and that is deliberate. Every Facets, QNXT or HealthEdge installation differs by version, configuration and local customisation; a generic connector would be a liability rather than an asset, and would have to be rewritten for each engagement anyway. Connector implementation is scoped as project work within a Platform Engagement, against a stable interface the platform already exercises.

Clearinghouse adapters

Interface scaffolding exists for Availity and Change Healthcare eligibility. These are not implemented today. We do not currently have Optum 360 or Inovalon adapters.

Multi-tenant isolation enforcement

The platform is architecturally multi-tenant — per-tenant data partitioning, tenant-scoped queries, tenant-aware configuration and audit. Tenant isolation is not yet independently enforced: tenant identity resolves from request context, and internal services currently assume a trusted network rather than authenticating callers themselves.

Deployments today are single-tenant, so there is no cross-tenant exposure. Enforcement — authenticated tenant identity and an authenticating gateway in front of internal services — is scheduled work, gated before any multi-tenant production deployment. We would rather state this than let you find it.

Other gaps we are closing deliberately

  • Reference customer — pre-sales with a first pilot partner. No production customer runs CHO as system of record yet.
  • Coordination of benefits when CHO is secondary or tertiary — primary adjudication and secondary detection ship today; secondary calculation is next.
  • Benefit augment / compare-against-legacy mode — Replace mode ships today; Augment mode is Phase 2.
  • X12 276/277 and 278 as X12 transactions, and inbound 835 parsing (outbound 835 generation ships today).
  • Test coverage on some core services — claims-service around 24% line coverage, provider-service around 12%, sponsor-service around 13%. These are the lowest-covered and the most operationally critical; they are on a known hardening backlog.
  • Cosmos DB parity with MongoDB — MongoDB is the reference and tested backend; some capabilities are MongoDB-only today.
  • Correspondence and letter generation — appeal decisions emit structured events today; the consuming correspondence service has not shipped.
  • Scale testing — not yet run against 10M+ claims/year production volume.

Architecture

Cloud Health Office runs as containerised .NET microservices on Kubernetes — local Docker Desktop, AKS, EKS, GKE, or customer-managed clusters. Services communicate over an event bus (Kafka or Azure Service Bus). Document persistence is MongoDB or Cosmos DB; PostgreSQL backs reference data; Redis accelerates cache and accumulators.

Argo Workflows orchestrates X12 file-transport and ingest pipelines — SFTP pickup, envelope handling, batch routing. Claims adjudication itself does not run on Argo: it runs as event-driven .NET services, which is the path the Million Claim Challenge measures. Both are current architecture; they do different jobs.

Secrets resolve through a pluggable provider — Kubernetes Secrets and environment variables by default, with Azure Key Vault and HashiCorp Vault available. No secret store is required to run the platform locally or to reproduce the benchmark.

Security Posture

Stated as what is implemented, what is templated, and what is your responsibility.

Implemented in the platform

  • SMART-on-FHIR OAuth scope enforcement on the external FHIR and partner APIs.
  • PHI-aware log redaction and log-injection sanitisation in application code.
  • Tenant-scoped data access with per-tenant partitioning.
  • Pluggable secret management — Kubernetes Secrets, Azure Key Vault, or HashiCorp Vault with Kubernetes auth, so no long-lived credential is stored in the application.
  • Secret scanning, dependency scanning, container scanning and a PHI-validation gate in continuous integration.

Provided as reference infrastructure templates

Bicep templates provision private endpoints for PaaS dependencies, Key Vault Premium with HSM-backed keys, and configurable audit retention (default seven years). These are templates you deploy and validate in your own subscription — not a managed service we operate for you today.

Your responsibility

Conditional Access policies, multi-factor authentication, and identity governance are configured in your Entra ID tenant. Administrative and physical safeguards are defined per engagement. Confirm every cloud service in scope is eligible for PHI workloads under your own agreements.

Known gaps

Internal services do not currently authenticate callers and rely on network trust; tenant isolation is not independently enforced. See On the roadmap. This is appropriate for single-tenant deployment behind your own controls and is being hardened before multi-tenant production.

Regulatory Posture

We make no compliance or certification claims. Specifically:

  • Aurelianware does not hold SOC 2 Type II or HITRUST certification.
  • We do not claim the platform is "HIPAA compliant." HIPAA compliance is a property of your deployment, your agreements and your operating practices — not of software. The licence carries no warranty of HIPAA compliance.
  • We do not claim CMS-0057-F compliance. We provide implemented technical surfaces against the rule; compliance requires your integration, configuration and legal review.

What we do provide is a readiness matrix that distinguishes "implemented" from "integration required" from "phase 2", so you can scope the gap honestly.

Evaluating It Yourself

The platform is source-available. The fastest honest evaluation is to run the benchmark yourself rather than read about it.

# 1. Clone
git clone https://github.com/aurelianware/cloudhealthoffice.git
cd cloudhealthoffice

# 2. Deploy to local Kubernetes (Docker Desktop)
bash ./scripts/deploy-local.sh

# 3. Run a scored 1,000-claim validation first
CLAIMS=1000 MAX_CLAIMS=1000 PARALLELISM=10 PROGRESS_EVERY=100 \
  JOB_NAME=mcc-quickstart-1k ./scripts/run-mcc-local-k8s.sh

# 4. Inspect the published run in the portal
kubectl port-forward -n cloudhealthoffice svc/portal 8080:80
# http://localhost:8080/mass-adjudication-runs

Scale up deliberately — 10K as a confidence gate, then 100K, then the full corpus. No secret store, cloud subscription or licence key is required for any of this.
