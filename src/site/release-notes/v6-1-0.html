v6.1.0: Spartacus

Released
October 31, 2026
Previous release
v6.0.0

On this page

  • Highlights
  • Upgrading from 6.0
  • Where this release has been validated
  • Off by default
  • Not yet done for CMS-0057-F

This release covers the pull requests merged since v6.0.0 (#1583 to #1651). It is a minor version: nothing in it requires a configuration change to upgrade from 6.0, and everything new that changes behaviour is off until a deployment turns it on.

It closes most of what the v6.0.0 notes listed as not yet done for CMS-0057-F: SMART Backend Services authentication, the Plan-Net 1.2.0 Provider Directory and the rest of Bulk Data $export. Work planned for 6.2 (mid-December) landed here too. What is still open is under Not yet done for CMS-0057-F.

"I'm Spartacus": a backend client now proves who it is with its own signed assertion, and CHO can do the same to other payers.

Highlights

SMART Backend Services, in both directions (G-42)

  • Inbound (#1583): a tenant administrator registers a backend client with its public keys (jwks or jwksUri) instead of a secret. The client gets client_credentials tokens with a private_key_jwt assertion (RS384 or ES384, single-use jti, exp at most five minutes out). PUT /api/admin/smart/clients/{clientId}/keys rotates the keys.
  • For a provider (#1585): a backend client registered with providerId gets tokens carrying provider_id, and fhir-service treats it as that provider for Provider Access, including bulk Group/{providerId}/$export.
  • Outbound (#1587): for Payer-to-Payer as the new payer, CHO signs its own assertions to the other payer's token endpoint, caches the token, and publishes its public keys at /fhir/r4/.well-known/smart-backend-jwks.json.
  • Evidence: the hosted Inferno Bulk Data kit's SMART Backend Services group passed against the GKE demo on 2026-10-29 (#1598, #1606), and the nightly run now includes that group (#1607).

The public Provider Directory is Plan-Net 1.2.0 (G-36)

  • /fhir/r4/directory/{directory}/ serves all nine Plan-Net profiles, including the plan's own payer Organization, with every SHALL search, chain, _has, _include and _revinclude of the Plan-Net CapabilityStatement (#1584).
  • Each directory is an in-memory snapshot, rebuilt in the background every PublicProviderDirectory:RefreshMinutes (60).
  • The GKE deploy can now publish directories from one setting, PUBLIC_PROVIDER_DIRECTORY (#1608). Before, only the interop profile could.
  • The Inferno Plan-Net kit runs nightly with no token (INFERNO-PLANNET-SERVER-001). The kit is generated from Plan-Net 1.1.0, so check its known mismatches before treating a finding as a CHO defect.

Bulk Data $export is complete (G-34, G-35), still off by default

  • Claims-history attribution feeds a provider's Group export (#1586), so a plan that relies on it alone no longer exports nobody.
  • Patient/$export (#1588), and GET kick-offs on every export endpoint.
  • Payer-to-Payer over bulk: PayerToPayer/$export for consented members (#1589), PDex Group/$bulk-member-match and Group/{id}/$davinci-data-export (#1590), and outbound bulk with CHO as the new payer (PayerToPayer/$bulk-initiate, #1591).
  • _typeFilter and patient (#1594).
  • Fixes from the first Inferno Bulk Data run (#1592), and bulk jobs now read CHO's own services in the export's tenant (#1589).

Prior authorization reporting

  • Appeal outcomes the PA reporting ledger refused can be listed and re-queued by an appeals:admin operator, from the API or the portal case screen (#1596).

Conformance testing

  • The nightly interop job now runs the Bulk Data kit (#1593) and the Plan-Net kit, and the kits actually boot: database migration (#1597), seed fixes (#1597, #1604) and harness fixes (#1605). From 2026-10-24 to 2026-10-28 the job had failed silently and produced no verdicts.
  • The GKE demo can be put in front of hosted Inferno on public tunnel hostnames, opt-in (#1598, #1606). Runbook: docs/deploy/GCP-CONFORMANCE-TESTING.md.
  • The harness now reaches the kits and reports honestly: sized request bodies instead of chunked ones (#1611), its own faults kept apart from CHO failures (#1612), the kit's own tokens (#1614), authorization-service and an Encounter in the interop stack (#1616), and the validator's reason on each failing test (#1617).

Fixes from the first Inferno results

The first runs that produced kit results found real CHO defects. Fixed:

  • FHIR codings pass terminology validation: dotted ICD-10-CM codes, BCP-47 language display names, NUCC display names (#1620).
  • The US Core searches the kit makes no longer answer 400 (#1621), and POST [type]/_search is served as the equivalent GET search (#1615).
  • CARIN BB: the CapabilityStatement instantiates C4BB, local line codes are marked not-applicable, EOBs declare the versioned profile and a payee, Coverage supports _include, and EOB search applies the CARIN BB search parameters (#1623, #1625).
  • A patient launch's token response now carries the patient and encounter launch context SMART App Launch requires (#1625).
  • Interop fixture: a second member for Bulk Data, and a Plan-Net network address and plan document URL (#1622, #1624).
  • Later runs found more, also fixed: the public directory links practitioners, affiliations, locations and endpoints as Plan-Net expects (#1626, #1636, #1639); FHIR date search matches an instant only at its stated precision (#1632); CARIN BB Coverage carries the subscriber and relationship, and C4BB Practitioner is served (#1649); Practitioner search honours _lastUpdated (#1651).

X12: CAQH CORE real-time and dental claims

  • CAQH CORE real-time eligibility (#1641, #1643): with CoreConnectivity:Enabled, eligibility-service answers CORE Connectivity vC2.2.0 envelopes at /core/eligibility (SOAP 1.2 or MIME multipart), a 270 in and its 271 back, following the CORE eligibility data content rule. Submitters authenticate by client certificate, username and password, or a CHO OAuth token.
  • CAQH CORE real-time claim status (#1642): claims-service answers a 276 with its 277 at /core/claimstatus, only for claims of the subscriber the 276 names.
  • CORE system availability (#1644): the weekly downtime and planned windows are published at GET /core/eligibility/availability, with availability measured against the 86% rule.
  • Dental claims (837D) (#1637): intake parses SV3 and TOO, keeps tooth and oral-cavity data on the claim lines, and SNIP validation knows the 837D. Two Medicaid dental prior-authorization demo stories ship as seed-dental (#1638).

Demo, site and documentation

  • The demo portal has a guided tour, a scripted prior-authorization story and a recorded walkthrough, with a prospect-access runbook (#1618, #1619).
  • The website publishes the nightly Inferno results and a per-kit explainer (#1630, #1631), and claims it could not back were removed (#1628).
  • New core adapter implementer guide (#1648), diagrams of where CHO plugs into the CMS APIs (#1633), and a refreshed architecture overview (#1650).

The full list, itemized, is in the changelog.

Upgrading from 6.0

No steps are required. Things to know:

  • Public directory resources changed shape. Practitioner, PractitionerRole and Organization now declare only the Plan-Net profiles, and PractitionerRole carries Plan-Net codes instead of the CHO tier and secondary specialties. The authenticated /fhir/r4/ routes are unchanged. This matters only to a plan that published a directory on 6.0.
  • A cancelled bulk export's status URL answers 404 (it was 410), as Bulk Data 2.0 requires. Only deployments with BulkExport:Enabled are affected.
  • .well-known/smart-configuration now advertises private_key_jwt algorithms, client-confidential-asymmetric and the refresh_token grant.
  • To publish a directory, each plan still needs its PublicProviderDirectory:Payers:<id> entry with an address; Plan-Net fails without it. See docs/architecture/public-provider-directory.md.

Where this release has been validated

  • Hosted Inferno, against the GKE demo: Bulk Data v2.0.0 SMART Backend Services group, pass (2026-10-29). The export groups have not been run on hosted Inferno.
  • Inferno kits against the seeded interop-cho profile: US Core 3.1.1, CARIN BB 2.0.0, Da Vinci Plan-Net and Bulk Data 2.0.0 (with its SMART Backend Services group) all pass on main at this release's commit (DaVinci Interop run 41168269450, 2026-10-31), apart from the known kit issues below. The results are also on the website at /evidence/inferno-conformance.
  • Known kit issues, not counted as failures (listed with their reasons as infernoKnownKitIssues in interop/scenarios.json; see "Known kit issues" in docs/interop/davinci.md):
    • CARIN BB (carin-for-blue-button-test-kit v0.16.3, the latest release): the five EOB subtype validation tests (inpatient institutional, outpatient institutional, oral, pharmacy, professional non-clinician). Each checks every EOB the kit collected against that one subtype's profile, so a member with more than one claim type always fails them. Each EOB is still validated against its own profile on the conformance goldens.
    • Plan-Net (davinci-plan-net-test-kit v0.13.4, the latest release): 25 forward-chain search tests. The kit takes the chained value from the first resource of that type it collected, which is often the payer Organization that nothing references, and then fails on an empty result. CHO's chained search is covered by PlanNetSearchEngineTests, and the forward chains whose first candidate is referenced pass. The kit is also generated from Plan-Net 1.1.0, while CHO serves 1.2.0.
  • Google Cloud (GKE): the demo is deployed on every merge to main.
  • Azure: automatic deploys are still paused (AZURE_DEPLOYMENTS_ENABLED) behind the #1217 deployment checklist. Neither 6.0 nor 6.1 has been deployed to Azure.

Not yet done for CMS-0057-F

The Patient Access, Provider Access and Payer-to-Payer API requirements take effect on January 1, 2027. Still open after 6.1:

  • Hosted Inferno for the export groups. The nightly kits pass, but the Bulk Data export groups have not been run on hosted Inferno against an HTTPS deployment (G-60).
  • System-level $export still answers 501; no caller has been approved for it.
  • No X12 278 bridge. CHO relies on HHS enforcement discretion for FHIR-based prior authorization without a 278.
  • Per-issuer scope limits (G-39), so only named issuers can mint system/PayerToPayer.read, are not built.

A plan must also supply some things itself:

  • the PA-DECISION-EXTENSION letter template;
  • its PublicProviderDirectory entry, with the plan's address;
  • its counsel's reading of "more than once" for the Patient Access usage figures. The usage ledger counts only from the day 6.0 or later is deployed, so days before that need another source.

docs/epa-gap-matrix.md gives the status of every requirement.
