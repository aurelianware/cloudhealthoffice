Architecture

Cloud Health Office is a Kubernetes-native, multi-tenant platform for health plan operations: claims administration, the CMS-0057-F interoperability APIs, and HIPAA X12 transactions. It runs beside an existing core admin system or progressively replaces it, in the plan's own cloud or operated for it.

Calculation Engines

Benefit Engine (HDHP/HSA, aggregate family accumulators, DRG inpatient), Fee Schedule Engine (DRG lookup, Medicaid cross-schedule, multiple procedure ranking), NCCI Engine, COB Engine, Risk Adjustment Engine, Encounter Engine, Claims Scrub Engine, Capitation Engine, and Operating Mode Engine.

X12 Processing

Inbound parsers for 837 claims, 834 enrollment, 820 premium payment, 270 eligibility, and 276 claim status. Outbound builders for 271, 277, 835, 834, 999, and TA1. All written in C# with no third-party EDI library. Batch files arrive over SFTP and are orchestrated with Argo Events and Argo Workflows.

CMS-0057-F Interoperability APIs

The FHIR service serves the CMS Interoperability and Prior Authorization Final Rule APIs, and the CMS-9115-F APIs they build on, as FHIR R4.

APIWhat it servesImplementation guides
Patient AccessClaims, encounters, clinical data, coverage, and prior authorization decisions for a member's own appUS Core 3.1.1, CARIN Blue Button 2.0.0, PDex
Provider AccessThe same data for in-network providers, scoped to their attributed members, with member opt-outPDex, Bulk Data, SMART Backend Services
Payer-to-PayerMember match and data exchange with a member's previous or concurrent payer, one member or in bulkPDex Payer-to-Payer, HRex member match, Bulk Data

The FHIR service also computes the Patient Access usage metrics plans report to CMS. Bulk export jobs are durable, their files expire after 24 hours, and the feature is enabled per deployment. The public Provider Directory is the one unauthenticated route: it ignores any credential on the request, serves only directory resources, and exists only for plans that have published a directory. See the CMS-0057-F compliance guide for requirement-by-requirement coverage.

Real-Time Eligibility and Claim Status

Trading partners and clearinghouses send real-time 270 eligibility and 276 claim status inquiries over CAQH CORE Connectivity (SOAP 1.2 and MIME) to /core/eligibility and /core/claimstatus. Submitters authenticate with an X.509 certificate, username and password, or OAuth, and each is registered to one tenant. The shared processor handles TA1 and 999 rejections, response time budgets, and published downtime schedules.

Claims Adjudication Pipeline

The 10-step pipeline takes an 837 from ingestion to a final, explainable outcome with full benefit calculation.

Pipeline Steps

The pipeline executes: get claim, validate codes, verify coverage, validate provider, check prior auth, get benefits, apply NCCI/MUE edits, calculate allowed amount, calculate cost-sharing (copay/coinsurance/deductible), and update claim status. Each step is individually testable and observable. A claim can correctly finish as paid, denied for a valid business reason, or pended for review, and the platform keeps those outcomes separate from platform errors.

Multi-Tenant Design

Every authenticated request carries an access token whose signature, issuer, audience, and lifetime are validated before anything else runs. The tenant comes from a claim in that token, and it drives data isolation, configuration routing, and audit logging. An X-Tenant-ID header is accepted only when it matches the token's tenant, so a caller cannot reach another plan's data by changing a header.

Identity and access

CHO's SMART authorization server supports SMART App Launch for member and provider apps and SMART Backend Services (client_credentials with signed JWT client assertions) for systems such as Provider Access and Payer-to-Payer exchange. A token service issues scoped service-to-service tokens, and plans that already run an identity provider such as Entra ID can federate it.

Core admin adapters

A plan does not have to replace its core admin system. Each domain has its own adapter contract, and the tenant's configuration selects the implementation. CHO-native implementations are complete. QNXT, Facets, and HealthEdge connectors are contracts that are built per engagement under the plan's own vendor license, guided by a published implementer guide and conformance tests.

Conformance Evidence

Every night, CI starts the full stack and runs the ONC Inferno test kits for US Core 3.1.1, CARIN Blue Button 2.0.0, Da Vinci Plan-Net, and Bulk Data 2.0.0 with SMART Backend Services, plus Da Vinci scenario tests for PAS, CRD, and DTR against reference implementations. Results are published on the Inferno conformance evidence page. An Inferno pass is evidence, not CMS certification. The Million Claim Challenge does the same for claims correctness and throughput.

HIPAA Security

The platform addresses HIPAA technical safeguards through five layers of defense in depth for PHI:

  • Private endpoints — network isolation of PHI with no public IP addresses exposed.
  • PHI masking — Application Insights redaction using DCR-based rules.
  • BYOK encryption — customer-managed encryption keys.
  • 7-year data lifecycle — automated tiering and retention.
  • CI/CD PHI checks — automated gates designed to keep PHI out of logs and telemetry.
