CMS-0057-F Compliance Guide

Cloud Health Office delivers a CMS-0057-F readiness surface — FHIR R4 APIs, X12 EDI mapping, SNOMED–CPT–ICD terminology translation, and multi-source provider verification — designed to be validated alongside existing payer core admin systems.

Where things stand (November 22, 2026)

Eight of nine ONC Inferno test kits pass against Cloud Health Office’s CMS-0057-F FHIR APIs: US Core, CARIN Blue Button, Da Vinci Plan-Net, Bulk Data with SMART Backend Services, Da Vinci PDex (payer-to-payer member match), Da Vinci DTR, Da Vinci CRD and SMART App Launch 2.2. The ninth, Da Vinci PAS, passes every prior authorization use case; six must-support tests for optional response content are still open and are logged as gaps. The kits run every night on the main branch. No CMS-0057-F acceptance scenario is a GAP any more: 6 of 21 are PASSABLE and 15 are PARTIAL. What remains is listed in the roadmap below.

Stated plainly: these results come from a test stack with synthetic data, not a production deployment. An Inferno pass covers the groups that ran at that kit version; it is not ONC, CMS or HL7 certification, and CMS-0057-F has no certification program for payer APIs. Each plan’s data mapping and deployment still has to be validated in its own environment.

What is CMS-0057-F?

CMS-0057-F (Advancing Interoperability and Improving Prior Authorization Processes) is a final rule requiring health plans to implement specific FHIR R4 APIs to improve prior authorization workflows, reduce provider burden, and enhance patient care coordination.

The rule applies to Medicare Advantage organizations, state Medicaid and CHIP fee-for-service programs, Medicaid managed care plans, CHIP managed care entities, and QHP issuers on the federally facilitated exchanges. CMS enforces it through each program’s existing oversight: Medicare Advantage contract compliance, state Medicaid and CHIP oversight of managed care contracts, and QHP certification.

Deadline: January 1, 2027

All impacted payers must have Patient Access, Provider Access, Payer-to-Payer, and Prior Authorization APIs live in production by this date. Cloud Health Office is designed to help payers stand up and validate that readiness surface without replacing the core admin system first.

Achieving compliance requires more than standing up four FHIR endpoints. The rule depends on Da Vinci Implementation Guides (PAS, CRD, DTR, PDex) that exchange clinical data in SNOMED CT — a code system that payer core admin platforms do not natively speak. It also requires provider directory accuracy and real-time eligibility verification against validated provider records. CHO is built to address the full compliance surface in a single deployable stack: APIs, EDI transformation, terminology translation, and provider data integrity.

Compliance Dashboard

Two kinds of evidence are published, and they are kept separate. Conformance kits are tests we did not write: the ONC Inferno kits, and exchanges with the HL7 Da Vinci reference implementation. A kit pass never changes an acceptance status, and the two are never added into one score.

Required APIs

Patient Access API

Empowers patients to access their complete health data electronically — claims history, Explanation of Benefits, clinical data, coverage, and eligibility. Claims are served as CARIN Blue Button ExplanationOfBenefit resources. Patient, Coverage, Encounter and Claim come from Cloud Health Office’s own services, and claims a plan’s core already adjudicated can be loaded from CPCDS extracts. Prior authorizations, with their status, dates and denial reasons, are served to the member as preauthorization EOBs, with drugs excluded. Secured with SMART on FHIR. The Inferno US Core and CARIN Blue Button kits pass. Still open: clinical (USCDI) resources beyond Patient and Encounter come only from payer-to-payer imports today.

Provider Access API

Gives in-network providers access to member clinical and claims data with appropriate consent. An attributed provider is served unless the member has opted out, as the rule requires, and attribution includes members found in claims history. Bulk FHIR Group/$export and Patient/$export for a provider’s attributed panel are built and authenticated with SMART Backend Services; the Inferno Bulk Data kit passes. Bulk export is off by default and is switched on per deployment. Provider identity is validated against CHO’s multi-source provider verification engine.

Payer-to-Payer API

Enables data exchange when members switch health plans. The member’s opt-in arrives as an HRex Consent naming the requesting payer, and only that payer is served. HRex $member-match passes the Inferno PDex kit. Bulk transfer is built (PayerToPayer/$export, PDex Group/$bulk-member-match and $davinci-data-export), off by default, and the export carries the member’s claims and prior authorizations with financial data removed. Outbound requests, where CHO is the new payer, are built behind a transport seam. Still open: validating the export as PDex, and Inferno coverage of CHO as the requesting payer.

Prior Authorization API

Converts the prior auth workflow from phone/fax to real-time FHIR-based requests. Uses the Da Vinci PAS, CRD and DTR implementation guides. PAS $submit stores a durable authorization record before it answers; CRD and DTR exchanges pass against the HL7 Da Vinci reference implementation, and the Inferno DTR 2.2.0 kit passes. Decision deadlines (72 hours expedited, 7 calendar days standard) are persisted from receipt, with the one lawful 14-day extension, and every denied or reduced line carries a coded reason. CHO relies on HHS enforcement discretion for FHIR-only prior authorization; there is no X12 278 bridge, though authorizations a core decided can be imported from X12 278 files. See the ePA gap matrix.

The Prior Authorization API depends on three foundational capabilities that most competing implementations leave as “customer responsibility”:

  • Coverage Requirements Discovery (CRD) — Real-time coverage rules evaluated during the provider workflow via CDS Hooks. Requires SNOMED-to-CPT/ICD translation to match clinical codes against payer benefit configuration. CHO's Terminology Crosswalk handles this natively.
  • Documentation Templates & Rules (DTR) — FHIR Questionnaire and QuestionnaireResponse for automated clinical documentation collection. Questionnaire answer codes can be resolved across code systems by the crosswalk engine. Questionnaire packages follow DTR 2.2.0 with CQL pre-population (built for the MRI form) and adaptive forms through $next-question.
  • Provider Identity Verification — Authorization requests must be validated against credentialed, non-excluded providers. CHO's Provider Verification engine screens against NPPES, OIG/LEIE, PECOS, and state licensing boards in real time.

Terminology Translation

CMS-0057-F's Da Vinci workflows (CRD, DTR, PAS) exchange clinical data in SNOMED CT — the terminology used by EHRs and clinical decision support systems. But payer core admin platforms (QNXT, Facets, HealthEdge, Amisys) store and adjudicate claims using CPT and ICD-10-CM codes. This terminology gap is the most commonly overlooked compliance obstacle.

The problem often left to the payer

Without built-in terminology translation, a prior authorization request containing SNOMED CT code 73211009 (Diabetes mellitus) cannot be matched to the payer's ICD-10-CM benefit configuration (E11.9, E10.9, etc.). Implementations often treat this as “out of scope” or “customer responsibility”, leaving payers to build their own translation layer or buy a separate product. CHO includes it.

CHO's Terminology Service implements the FHIR R4 ConceptMap/$translate operation with a multi-tier mapping architecture:

Context-aware disambiguation

Many SNOMED CT concepts map to multiple target codes. SNOMED 73211009 (Diabetes mellitus) can map to E10.x (Type 1), E11.x (Type 2), E13.x (Other specified), or O24.x (Gestational). CHO's context rule engine uses patient demographics, co-morbidities, and plan-specific coding policy to select the best match — not just the first match.

Where the crosswalk fits in CMS-0057-F

The Terminology Service is consumed by three CHO microservices at runtime to fulfill CMS-0057-F requirements:

  • CRD Server — Translates SNOMED CT codes from EHR CDS Hook requests into the payer's CPT/ICD code space, then checks against benefit configuration to determine prior auth requirements.
  • PAS Server — Designed to translate procedure and diagnosis codes using $batch-translate (X12 278 ↔ FHIR conversion is planned) for low-latency bulk translation in real-time prior auth decisions.
  • DTR Engine — Resolves questionnaire answer codes across code systems so pre-populated FHIR QuestionnaireResponse values are clinically accurate and machine-readable.

Provider Verification & Integrity

CMS-0057-F requires a Provider Directory API and provider data accuracy for the Provider Access API. Authorization requests, claims adjudication, and provider directory lookups all depend on verified, current provider records. CHO's Provider Verification Engine aggregates data from five authoritative federal and state sources into a composite Provider Integrity Score (0–100) per NPI.

Data SourceWhat It ChecksUpdate Frequency
NPPES (NPI Registry)NPI validity, practice address, taxonomy, enumeration statusDaily
OIG / LEIEFederal exclusion screening — excluded providers cannot participate in federal programsMonthly
PECOSMedicare enrollment status and participation eligibilityMonthly
CMS Open PaymentsIndustry relationship disclosure for transparency and conflict-of-interest awarenessAnnually
FSMB / State LicensingActive medical license verification, disciplinary actions, multi-state compact statusVaries by state

The composite score is computed using a weighted algorithm across all five sources. Providers below a configurable threshold (default: 60) are flagged for review. Excluded providers (OIG/LEIE match) are automatically blocked from authorization and claims processing. All verification results are audit-logged with timestamps and source data versions for compliance documentation.

Where provider verification fits in CMS-0057-F

  • Provider Access API — Provider identity is verified before granting access to member clinical and claims data. NPI is validated against NPPES, exclusion status is checked against OIG/LEIE, and license status is confirmed.
  • Prior Authorization API — Requesting and servicing provider NPIs are verified during PAS submission. Excluded or unlicensed providers trigger an automatic deny with structured rationale.
  • Provider Directory API — Directory entries are enriched with verification metadata, ensuring that provider information exposed through FHIR endpoints reflects current, validated data.
  • Claims Adjudication — Step 4 of the 10-step adjudication pipeline validates the servicing provider before benefit calculation proceeds.

Augment, don't replace

CHO deploys as a compliance layer alongside your existing core admin platform — QNXT, Facets, HealthEdge, Amisys, or any other system. No replatforming. No rip-and-replace. Your CAPS stays in place. CHO handles FHIR, EDI, terminology, provider verification, and CMS compliance. The ICoreAdminAdapter pattern means CHO can operate in Augment mode (compliance overlay on your CAPS) or Replace mode (standalone core admin) per tenant. The default way a core feeds CHO is the daily file drop: CPCDS members, coverage and claims, and UM authorizations as CSV or X12 278. Every CMS-0057-F API reads what the drop loaded, and the evidence above scores that path on its own. Live connectors that call the core per request (QNXT, Facets, HealthEdge) are an optional integration point, built and validated during an engagement for a plan that prefers them.

Roadmap: what remains

Everything below is open work, listed so a plan can see it before it signs anything. Each plan’s go-live date and sequencing are agreed in its own implementation plan.

Before January 1, 2027

  • Patient Access: serve clinical (USCDI / US Core) resources from a plan’s own sources, not only from payer-to-payer imports.
  • Payer-to-Payer: validate the export against PDex profiles, and run the Inferno PDex payer-client suite with CHO as the requesting payer.
  • Prior Authorization: run PAS $inquire against the HL7 Da Vinci reference implementation; full DTR answer validation and canonical resolution; close the six PAS must-support gaps (optional ClaimResponse elements, CDex requests inside PAS responses, replaced-authorization references).
  • Metrics: complete the CMS metric set and support each plan’s publication of its annual report.
  • SMART on FHIR: validate the full token response and SMART conformance in a production deployment (the Inferno SMART App Launch 2.2 kit passes on the test stack).
  • Per plan: load and validate the plan’s own data, then run the same Inferno kits against its deployment (./scripts/interop/run.sh deployment).

Planned

  • SOC 2: Aurelianware plans to pursue a SOC 2 examination. No SOC 2 report exists today; see Trust & security for the current security posture and what is not claimed.
  • Live core connectors: optional QNXT, Facets and HealthEdge connectors, built and validated with a plan that prefers them over the file drop. Off by default and not scored.
  • File-drop gaps: write-back of prior-authorization decisions into the plan’s UM system, and clinical data in the drop.
  • System-level bulk export: not served today; not required by CMS-0057-F.

Verify it yourself

You don’t have to take our word for any of this. The Inferno kits are free and public, and so is the harness that runs them. From a clone of the repository:

# Run every pinned Inferno kit against a local Cloud Health Office stack (Docker)
./scripts/interop/run.sh inferno all

# Or one kit: us-core | c4bb | plan-net | bulk-data | pdex | dtr
./scripts/interop/run.sh inferno dtr

# Exchange PAS, CRD and DTR with the HL7 Da Vinci reference implementation
./scripts/interop/run.sh br-payer all

# Point the US Core, CARIN BB and Plan-Net kits at a deployed CHO
CHO_INTEROP_TARGET_URL=https://your-cho/fhir/r4 ./scripts/interop/run.sh deployment

The same kits are hosted at inferno.healthit.gov, so a plan can point them at a Cloud Health Office sandbox, or at any vendor’s, and read the findings for itself. The nightly results, including the excused kit issues, are on the Inferno conformance page.
