Deployment Guide

Cloud Health Office is cloud-native: containerized .NET services on Kubernetes, with MongoDB-compatible storage, Kafka and Redis. The same manifests run on a laptop, on Azure (AKS) and on Google Cloud (GKE), so a plan chooses where it runs and who operates it.

Choose an operating model

Every model runs the same source-available software in a tenant dedicated to one plan. The right choice depends on your cloud standards, security requirements, engineering capacity and desired level of operational control. Compare the operating models in detail.

Path 1: Local evaluation

Runs the full platform on Docker Desktop Kubernetes, with MongoDB, Redis and Kafka in the same namespace and service-DNS layout used in the cloud. Synthetic data only. See the Kubernetes quickstart for the walkthrough.

# Build and deploy everything to Docker Desktop Kubernetes
./scripts/deploy-local.sh

# Check the services
kubectl get deployments -n cloudhealthoffice

Path 2: Google Cloud (GKE) reference deployment

Terraform in infrastructure/gcp/ creates a GKE cluster, an Artifact Registry repository, a documents bucket and keyless GitHub Actions access through Workload Identity Federation. The deploy-gcp-gke.yml workflow builds the images and applies the same service manifests used locally.

# Create the environment
cd infrastructure/gcp
terraform init
terraform apply -var="project_id=YOUR_PROJECT_ID"

# Then run the "Deploy demo to GKE" workflow, or scripts/deploy-gke.sh
Reference deployment, not a production environment

As shipped, this environment is for evaluation with synthetic data. A production deployment on Google Cloud adds a Google BAA, customer-managed encryption keys, a private cluster with Private Service Connect, production token signing, and managed services for state (Managed Service for Apache Kafka, Cloud Storage, and Secret Manager or HashiCorp Vault). See GCP-DEMO.md for the full list.

Path 3: Azure (AKS)

Bicep templates in infrastructure/azure/ provision the Azure environment, and the deploy-azure-aks.yml workflow deploys the services to AKS with keyless OIDC authentication from GitHub Actions.

# Copy and fill in the parameters (base name, SFTP and messaging settings)
cp infrastructure/azure/main.parameters.example.json main.parameters.json

# Provision infrastructure into a resource group
az deployment group create \
  --resource-group YOUR_RESOURCE_GROUP \
  --template-file infrastructure/azure/main.bicep \
  --parameters @main.parameters.json
Production reference architecture

For the full production design on Google Cloud, including network, identity, data, operations and compliance, with the status of each component, see the reference architecture blueprint.

Other clouds and on-premises Kubernetes

The services depend on Kubernetes and the components above, not on one cloud's proprietary services. AWS (EKS) and on-premises clusters use the same manifests; infrastructure code and managed-service bindings for them are scoped per engagement. Talk to us about your environment.

Secret management

Services read secrets through one secret-provider interface, so the backing store is a configuration choice rather than a code change.

ProviderStatus
Kubernetes SecretsDefault
Azure Key Vault (Workload Identity)Implemented — see AZURE-KEYVAULT-INSTALLATION.md
HashiCorp Vault (Kubernetes auth)Implemented
Google Secret Manager, AWS Secrets ManagerPer engagement, behind the same interface

Configuration keys use the .NET hierarchy, for example MongoDb__ConnectionString as an environment variable or MongoDb--ConnectionString as a Key Vault secret name.

CI/CD

Deployments run from GitHub Actions without stored cloud credentials: OIDC federation on Azure and Workload Identity Federation on Google Cloud. Environment protection rules gate promotion between environments.

Post-deployment verification

# All pods running
kubectl get pods -n cloudhealthoffice

# Service health
kubectl exec -it deploy/claims-service -n cloudhealthoffice -- curl -s localhost:5001/health/live

# FHIR capability statement
curl https://api.your-domain.example/fhir/r4/metadata | jq .status
Before production traffic

Complete the Production Readiness Checklist, run an isolated restore using the Backup & Disaster Recovery Runbook, and test paging with the Observability & Incident Response Runbook before routing production traffic. Production use requires a commercial license.
