Claims API

Submit claims, follow them through adjudication, work pended claims, and generate 835 remittance.

The claims API is the HTTP surface for the claim lifecycle in Cloud Health Office. It is served by two services: the claims service (submission, search, adjudication outcomes, the pended-claim work queue, adjustments and FHIR ExplanationOfBenefit) and the payment service (payment runs, reversal runs and 835 envelopes). This page is an orientation to that surface. Each service also serves its full OpenAPI description through Swagger in development environments.

Conventions

Authentication and tenant isolation

Every endpoint requires a bearer token and is permission-gated. The tenant comes only from a tenant claim inside the validated token: a token without one is rejected with 401, and an X-Tenant-ID header is accepted only when it matches the token’s tenant. A header naming a different tenant is rejected with 403. Every query is filtered by tenant. See Tenant Security.

Adjudication outcomes come from the pipeline

No endpoint writes an adjudicated outcome directly onto a claim. Submitting a claim hands it to the adjudication pipeline (NCCI edits, pricing, benefits and accumulators), which sets Approved, Denied or Pended. A pended claim is changed through the work queue, which re-runs the pipeline; payment status comes from remittance; and voids go through the void endpoint. The status endpoint returns 422 if it is asked to set an outcome status.

Status codes

CodeMeaning
200 / 201 / 204Successful read, create, or mutation without a body
202Accepted for asynchronous processing
400Validation failure
401 / 403Missing or invalid token; tenant or permission mismatch
404Not found within the caller’s tenant
409State-transition or idempotency conflict
422Well-formed request rejected by a business rule

Idempotency

Finalizing and voiding a claim are idempotent: the first call performs the transition and emits its event, and repeats are no-ops. Payment and reversal runs can be re-executed; partial failures are recorded as per-run warnings instead of failing the run. A claim can have only one adjustment per version, enforced by the data store.

POST/api/v1/claims/import/raw837Upload a raw X12 837 file; each claim in it is submitted through the same path

GET/api/v1/claims/import-transactionsHistory of 837 imports, with SNIP warnings at /import-transactions/snip-warnings
POST/api/claimsLegacy submission. Deprecated: responses carry Deprecation and Link: rel="successor-version" headers pointing at /api/v1/claims, and it uses the same submission service so the audit chain stays continuous.

Pended claims work queue

Pended claims are worked by examiners through the work queue. Resolving or overriding a claim re-runs the adjudication pipeline and records the examiner’s action. The pended claim guide walks through the same flow in the portal.

POST/api/claims/work-queue/{claimId}/assignAssign to an examiner
POST/api/claims/work-queue/{claimId}/resolveResolve a pend and re-adjudicate
POST/api/claims/work-queue/{claimId}/overrideExaminer override, with audit

Adjustments and voids

Payment runs and 835 remittance

Payment runs pick up adjudicated claims, finalize them and generate X12 835 remittance. Reversal runs do the same for voids. Generated 835 envelopes are stored and retrieved over the API.

MethodPathPurpose
POST/api/PaymentRuns, /api/PaymentRuns/{id}/executeCreate a payment run, then execute it
POST/api/PaymentRuns/executeCreate and execute in one call
GET/api/PaymentRuns, /api/PaymentRuns/{id}List runs, or read one
POST/api/PaymentRuns/{id}/cancelCancel a run before it executes
POST/api/PaymentRuns/{id}/eft-fileGenerate the run’s EFT file
POST / GET/api/ReversalRuns and the same sub-pathsReversal runs for voided claims
GET/api/v1/era-envelopes, /{id}, /{id}/ediList 835 envelopes, read one, or download the raw X12 835

FHIR ExplanationOfBenefit

The claims service serves FHIR R4 ExplanationOfBenefit reads and searches at /fhir/ExplanationOfBenefit and /fhir/ExplanationOfBenefit/{id}, authenticated and tenant-scoped, with a Provider Access variant under /fhir/ProviderAccess/. For the CMS-0057-F Patient Access, Provider Access, Payer-to-Payer and Prior Authorization APIs, see the FHIR API reference and the API explorer.

Stability

  • /api/v1/* paths carry the V1 stability commitment: a breaking change gets a parallel /api/v2/* path before V1 is deprecated.
  • /api/claims/* is the versionless surface the Cloud Health Office portal uses. Changes are coordinated with portal releases and it is not committed to external consumers. The deprecated POST /api/claims will be removed after trading-partner integrations have moved to V1.
  • /fhir/* follows FHIR R4; new search parameters are additive.
  • Payment and reversal runs are operator-facing; changes are coordinated with the portal.
