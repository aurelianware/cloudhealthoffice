Conformance kit evidence

Judged every night by tests we did not write.

Four open-source Inferno test kits run against Cloud Health Office on a nightly schedule: US Core, CARIN Blue Button, Da Vinci Plan-Net, and Bulk Data with SMART Backend Services. The latest results are published below as the kits reported them, including the failures.

US Core · CARIN BB · Plan-Net · Bulk Data Kits pinned by release and commit Synthetic data Not certification

Inferno is the open-source FHIR conformance testing framework built for the ONC (the Office of the National Coordinator for Health IT). Each test kit encodes one implementation guide's requirements and drives an API the way a real client would. There is no public registry of payer results, so we publish ours here.

What is being judged

What each kit tests, and the requirement behind it

CMS-0057-F and the earlier CMS-9115-F require payer APIs built on FHIR R4 and the ONC API standards at 45 CFR 170.215. For the content of each API, CMS points to specific HL7 implementation guides. Each kit below checks one of those guides.

KitWhat it checksWhat Cloud Health Office runsRequirement it speaks to
US Core

us-core-test-kit v1.1.6

 The CapabilityStatement; read and the required searches on each profile; must-support elements; references that resolve; every returned resource validated against its US Core profile by the HL7 validator. Suite us_core_v311: the CapabilityStatement, Patient and Encounter groups. Those are the US Core resources a payer serves. The other clinical groups are not run. The ONC API standards that CMS-0057-F adopts by reference. US Core 3.1.1 is the floor, and it underlies Patient Access, Provider Access and Payer-to-Payer.
CARIN Blue Button

carin-for-blue-button-test-kit v0.16.3

 Patient, Coverage, ExplanationOfBenefit, Organization and Practitioner reads and searches, including EOB searches by type, identifier, service date and _lastUpdated, the _include parameters, and validation of each EOB against its claim-type profile. Suite c4bb_v200 financial groups, run as a member's SMART patient app with a token bound to that member, the way a consumer app reaches Patient Access. The Patient Access API: claims and encounter data for members, required since CMS-9115-F and expanded by CMS-0057-F. CARIN Blue Button is the guide CMS recommends for it.
Da Vinci Plan-Net

davinci-plan-net-test-kit v0.13.4

 All nine directory resource types: searches, forward and reverse chained searches, _include and _revinclude, must-support elements, and profile validation. The whole suite, against the public Provider Directory with no access token, because the rule says the directory is public. The Provider Directory API, required since CMS-9115-F and open to the public without authentication. Plan-Net is the guide CMS recommends for it.
Bulk Data + SMART Backend Services

bulk-data-test-kit v0.13.2

 SMART discovery and the Backend Services token endpoint, including refusals of a bad grant type, assertion type or JWT. Group and Patient $export: kick-off, status polling, the manifest, authorized NDJSON download, resource validation, cancel, _outputFormat and _since. Suite bulk_data_v200: the SMART Backend Services, Group export and Patient export groups. The client is a registered backend bound to a seeded provider. The Provider Access and Payer-to-Payer APIs, due January 1, 2027, which must support FHIR Bulk Data with system-to-system authorization.

Stated up front

Known kit issues and version gaps

A kit is software with a version, written against a specification that keeps moving. Where a kit can't judge any server, or checks a different version than the one we serve, it is listed here and in the snapshot, with the reason. Nothing is quietly dropped.

CARIN BB: three EOB claim-type checks

In kit v0.16.3, the latest release, the oral, pharmacy and professional non-clinician validation tests check every EOB the kit collected against that one claim type's profile. A member with both professional and institutional claims therefore fails the pharmacy profile on EOBs that never claimed it. No server with mixed claim types can pass these three tests. Their failures are still recorded, but they don't count against the result. Every other test counts.

CARIN BB: the non-financial suite is not run

The kit's non-financial suite checks the superseded -NonFinancial profile URLs from an April 2023 snapshot. Cloud Health Office declares the current CARIN BB 2.2.0 -Basis profiles, so the suite can't match its EOBs in either direction. We won't rename our profiles to an outdated draft just to turn it green.

Plan-Net: kit 1.1.0, server 1.2.0

The kit is generated from Plan-Net 1.1.0, while Cloud Health Office serves 1.2.0. Most requirements are unchanged between the two. Where they differ, the kit is checking the older version.

Bulk Data: TLS and system export

The nightly runs on a private plain-HTTP network, so the token-endpoint TLS test is switched off with the kit's own setting. That group passed over real TLS on hosted Inferno against our demo environment on October 29, 2026. The system-level export group isn't run, because Cloud Health Office doesn't serve system-level $export.

Reproducible

How the run works, and how to repeat it

The nightly job starts a Cloud Health Office stack and the four kits together on an isolated network. It seeds synthetic members, claims, coverage and a provider directory, checks that Cloud Health Office answers its own metadata endpoint, and then hands each kit its inputs. Each kit is pinned to a release tag and commit in interop/versions.json. The groups each kit runs, and the known kit issues, are listed in interop/scenarios.json. Changing either one takes a reviewed pull request.

You don't have to trust our runner. The same kits are hosted at inferno.healthit.gov, and the harness is in the public repository (./scripts/interop/run.sh inferno all). A health plan can point a kit at a Cloud Health Office sandbox, or at any vendor's sandbox, and read the findings for itself.

Stated plainly

What these results do not establish

Limitations

  • This is not certification. Running ONC's tool is not ONC, CMS or HL7 approval. CMS-0057-F has no certification program for payer APIs.
  • A pass covers the groups that ran, at that kit version. It isn't a pass of the whole implementation guide, and it isn't a pass of CMS-0057-F.
  • Synthetic data on a test stack. No production member data is involved, and no production deployment is claimed.
  • No prior authorization kit runs here yet. Prior authorization (CRD, DTR, PAS) is evidenced by exchanges with the HL7 Da Vinci reference implementation. The Da Vinci DTR and PDex kits are pinned but not run yet.
  • Kit results and acceptance results stay separate. A kit result never changes a CMS-0057-F acceptance scenario status, and the two are never combined into one score.
