Scaling a Payer Platform in Google Cloud · Part One

Scaling a Healthcare Payer Core Admin and Interoperability Platform in Google Cloud, Part One: Same Code, Different Cloud

Evidence scope: This engineering field note covers two days standing the platform up on a new Google Cloud project with synthetic data. It is about portability, not performance: the environment is a single 8-vCPU demo node, and no Google Cloud throughput figures are claimed. Published Million Claim Challenge numbers come from local Kubernetes.
View article source GKE runbook Terraform

The Azure field notes ended with a promise: after Azure, run the same exercise somewhere else and find out which lessons were Azure's and which were simply what happens when a real platform meets a real cloud. This is the first half of that answer. Over two days in October 2026, this platform went from no presence on Google Cloud at all to every service it deploys reporting ready on Google Kubernetes Engine. It took no application rewrite. The services, Kubernetes manifests and container images are the same ones that run on a laptop and on AKS. It did take a redesign forced by a brand-new billing account, two dependency breaks that had nothing to do with Google, and two genuine bugs that every environment had been carrying and only this one surfaced.

Why Google Cloud, and why now

Health plans rarely live in one cloud. Many run some workloads in Azure, some in AWS and some in Google Cloud, and a common plan for the next few years is to consolidate onto one of them. A core administration platform that only runs well in the cloud it was born in becomes one more thing holding a consolidation back. The claim this platform makes is that it is Kubernetes-native and cloud-portable. Google Cloud is where that claim gets tested by doing it, not by saying it.

The goal for Part One was deliberately narrow. Before any scale numbers, the first question was whether the whole platform comes up on GKE from the repository, repeatably, without editing application code: claims, benefits, eligibility, enrollment, FHIR, prior authorization, payments, the portal and the rest, along with the Kafka, MongoDB, Redis and Postgres they depend on.

What got built

Everything is code in the repository, so a health plan's platform team can read it, run it and tear it down.

  • Terraform (infrastructure/gcp) creates the cluster, an Artifact Registry repository for the service images with a cleanup policy, and Workload Identity Federation so GitHub Actions deploys without a service account key. The federation trusts tokens minted for this one repository only. An optional budget alert sits on top.
  • A manual GitHub Actions workflow builds the service images, pushes them to Artifact Registry and deploys. It can also skip the build and deploy an existing image tag, which mattered more than expected.
  • Kafka runs in-cluster under the Strimzi operator: three KRaft brokers, so the existing topic definitions apply unchanged.
  • MongoDB, Redis and Postgres run in-cluster too, with a small seed for a synthetic demo tenant.
  • A renderer (deploy/gcp/render_manifests.py) reads the same per-service manifests the local deploy applies and adjusts them for GKE: images from Artifact Registry, Google storage classes in place of Azure's, Azure-only tolerations removed, and the host settings the demo needs. The source manifests are not modified, so the Azure and local paths are unaffected.

The environment is demo-grade by design, and it says so. It holds synthetic data only. There is no public ingress; it is reached by port-forward. Its development signing key is public in the repository, so it must never hold real data. There is no Google BAA, customer-managed encryption key or private cluster. Those are the gaps between this and a HIPAA production deployment, and docs/deploy/GCP-DEMO.md lists them.

The first wall was not Google's

The first full workflow run failed before it reached Google Cloud at all. Nine image builds stopped at restore with NU1605, a package downgrade error. A grouped Dependabot update the day before had moved one cryptography package forward. Two other packages the solution pins centrally now sat below the version it required. The fix was to align the pins, but the lesson was the useful part. This solution already centralizes package versions precisely because grouped bumps have broken it before, and a single updated package can still pull a transitive floor past everything else. The same class of break happened again the next day with an Azure Storage package whose new version required a newer Azure.Core than the solution can take. That bump is now held back in Dependabot until the Azure package family moves together.

The second wall was a new billing account

The second run built every image, pushed them all and applied every manifest. Then nothing scheduled. GKE Autopilot tried to add nodes and Google Cloud refused: Quota 'SSD_TOTAL_GB' exceeded. Limit: 250.0. The CPU and external IP quotas were close behind, at 12 vCPUs and 4 addresses.

Those are the defaults for a new billing account. The fix looked like a form: request 500 GB of SSD, 24 vCPUs and 8 addresses. The request was declined, both through the API and in the console, even after the account was upgraded from the free trial to a paid account. The console was plain about why: based on the account's usage history, it was not eligible for an increase yet. The same wall stopped the Azure series, on a different cloud. A new subscription's default limits are a real constraint for anyone evaluating a platform in a fresh account, which is how evaluations usually start.

Waiting was one option. Fitting inside the limit was the better one.

Fitting a payer platform on one node

The cluster became a single-zone GKE Standard cluster with one e2-standard-8 node: 8 vCPUs and 32 GB of memory on standard, non-SSD persistent disk. That uses 8 of the 12 allowed vCPUs, one external address and none of the SSD quota. Autopilot stays one Terraform variable away for when quota allows.

Two changes made the platform fit on it.

  • Storage moved to a standard-disk class the deploy creates, for Kafka, MongoDB and every service volume.
  • A small resource profile lowers what each service reserves. Kubernetes schedules by requests, the CPU a pod reserves, not by what it uses. Most of these services sit idle at a few millicores and reserve far more. The small profile caps CPU requests at 50 millicores (250 for claims-service), runs one replica of each service and leaves limits unchanged, so any service can still burst when it is working. The services' combined reservations dropped to about 2.2 vCPUs.

Running the whole platform around the clock costs roughly seven dollars a day at list price, and the node pool scales to zero between sessions.

One more lesson came from the cluster definition itself. terraform validate passed. terraform plan, run against the real project, rejected it: the provider does not allow enable_autopilot = false alongside remove_default_node_pool. The field has to be left unset instead. Validation checks shape; only a plan against a real project checks what the provider will accept.

What GKE found that every environment had missed

The first deploy to the new cluster brought up Kafka, MongoDB, Postgres and Redis, and all but two of the 35 platform services. The two that failed were the most valuable result of the exercise, because neither was a GKE problem.

pricing-api restarted in a loop, timing out on MongoDB at localhost. Its Kubernetes manifest supplied the database connection under the standard MongoDb setting. At startup, the service copies its own PricingApi.MongoConnectionString setting into that MongoDb section, and that setting still held the localhost default from appsettings.json. The manifest's value was overwritten every time. The fix was one rename in the manifest. The bug had been there in every deployment that used that manifest.

benefit-plan-service started cleanly and never reported ready. Its readiness check failed on Redis's eviction policy. This service keeps accumulator state in Redis: the commit journal and the fences that stop a voided or denied claim from being counted twice. If Redis may evict that data under memory pressure, deductible and out-of-pocket totals can silently go wrong. The service refuses to report ready on any evicting policy, and the repository's own deploy notes say to run that Redis with noeviction. The shared Redis manifest still said volatile-lru. The check did exactly its job, by blocking a deployment that could have miscounted a member's out-of-pocket maximum. The manifest now matches the deploy notes.

Both bugs were in manifests shared with the local and Azure deployments. A clean environment, standing up the whole platform from nothing, exposed them.

Where it stands

After those two fixes, a redeploy from the existing image tag finished in under two minutes. Every deployment reported ready: 35 platform services plus Redis, alongside MongoDB, Postgres and a three-broker Kafka cluster, on one 8-vCPU node in us-west1. No application code changed to get there. The code changes were to manifests and package pins that were wrong everywhere, not just on Google Cloud.

Ready means each service's own readiness checks passed. They cover its database, cache and message bus connections, and for benefit-plan-service the accumulator integrity rule described above. Readiness is the cluster's opinion, so a scripted smoke test then checked from outside, over port-forward from a laptop. All ten checks passed: claims, benefit-plan and FHIR services live; the FHIR adapter reporting its data as synthetic; the FHIR CapabilityStatement; FHIR responses carrying adapter labels; the claims API rejecting a request with no token (401) and accepting a signed development token; and the portal answering.

What Part One does not show

Part One is about portability, not scale. One node with lowered reservations is the right shape for a demo and an evaluation. It is not a performance environment, and nothing here is a throughput number for Google Cloud. The published Million Claim Challenge figures come from local Kubernetes, and they stay there until they are rerun.

Part Two

Part Two is where scaling belongs. Once the account has the quota, the plan is to switch the cluster to Autopilot or a larger node pool, restore full resource reservations and replica counts, and run the Million Claim Challenge methodology on GKE: the same corpus, the same correctness checks and the same published evidence, so the numbers can be compared directly with the local runs.
