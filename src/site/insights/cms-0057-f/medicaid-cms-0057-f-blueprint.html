CMS-0057-F & Medicaid

The Medicaid CMS-0057-F Blueprint, Already Built and Tested

Most CMS-0057-F guidance for Medicaid agencies and managed care plans now agrees on the same checklist. Here is each item on it, what Cloud Health Office has built for it, the evidence you can check, and what is still open.

Series: CMS-0057-F & Payer Modernization Published: October 31, 2026 For: Medicaid managed care plans, state Medicaid IT & compliance leads

Read enough CMS-0057-F guidance written for Medicaid and the same blueprint keeps appearing. Stand up the four FHIR APIs. Put an access layer over legacy data instead of replacing the core. Connect to provider EHRs. Run it on scalable cloud infrastructure. Treat consent, identity and audit as design requirements. Pair the technology with governance and change management. Measure the results.

We agree with that blueprint. What most versions of it leave out is the evidence: which items exist as working software today, which have been checked by tests someone else wrote, and which are still somebody’s job. This page answers those questions for Cloud Health Office, one item at a time.

CMS-0057-F is the federal rule that requires Medicare Advantage, Medicaid, CHIP, and some exchange plans to offer FHIR APIs for patient access, provider access, payer-to-payer exchange, and prior authorization by January 1, 2027.

How to read the statuses

Built means working code on a production path with tests behind it. Built, off by default means a deployment switches it on. Partial means part of the requirement is met and the gap is named. Yours means it is the plan’s work, and software cannot do it for you. The requirement-by-requirement source of truth is the ePA gap matrix in the public repository, which is deliberately harsher than this page. Passing an Inferno test kit is not CMS certification or a legal determination of compliance.

01Who gets more time, and who doesn’t

The API compliance date is January 1, 2027. The rule gives state Medicaid and CHIP fee-for-service programs two kinds of relief: a state can ask CMS for a one-time extension of up to one year, and a state with at least 90 percent of its enrollees in managed care can ask for an exemption for its fee-for-service program. Both go through CMS, and neither is automatic.

Medicaid and CHIP managed care plans get neither. An MCO serving a state that has an extension still owes its own APIs on January 1, 2027. For most Medicaid members, that makes the managed care plan, not the state, the organization that has to be ready first.

The rule text, CMS guidance, your state contract and your counsel are the authority on how these provisions apply to you. This summary is for orientation.

03The five APIs

Patient Access (enhanced)

Members’ claims and encounters are served as CARIN Blue Button ExplanationOfBenefit resources under a member-bound SMART token. CMS-0057-F adds prior authorization data to this API, and Cloud Health Office serves each authorization (status, dates, items, quantity and denial reason) as a Da Vinci PDex prior-authorization EOB from its own authorization records. A disclosure ledger counts the members who used an app more than once, so the plan has the numbers for its annual Patient Access usage report. The plan files that report; the software computes it.

Checked by: the Inferno US Core and CARIN Blue Button kits. Open: terminology and reference-target checks beyond what the kits cover, and the CARIN kit issues listed on the results page.

Provider Access

Attributed in-network providers can retrieve a member’s claims, encounters and prior authorizations. Sharing is opt-out, as the rule requires: a member’s opt-out is recorded as a revocable consent, and the API refuses if it can’t read the consent registry. Bulk $export for a provider’s panel is built and switched off by default, because it needs a storage bucket and backend client registrations a deployment provides.

Checked by: the Inferno Bulk Data kit with SMART Backend Services, and the Provider Access security evidence. Open: attribution. Today it comes from configuration. A Medicaid plan’s real attribution, usually its PCP assignments, has to be fed in from the plan’s systems.

Payer-to-Payer

When a member moves between plans, the new plan asks the old one for up to five years of data. Cloud Health Office handles the member’s opt-in as an HRex Consent, runs $member-match, and returns claims, encounters and active or recent prior authorizations. Only a registered backend client for the receiving payer can call it. The bulk form is built and off by default, like Provider Access.

Checked by: the Payer-to-Payer evidence; the Da Vinci PDex kit is being added to the nightly run. Open: no exchange has yet been run against a real prior payer. Medicaid churn makes this API matter more than it does for most commercial plans.

Prior Authorization (CRD, DTR, PAS)

PAS stores the request and the decision before it responds, and inquiry returns the stored outcome. Decisions are recorded per service line, with a reason for every denial or reduction. Decision clocks start at receipt and are persisted: 72 hours for expedited requests and 7 calendar days for standard ones, with the one lawful 14-day extension modelled for Medicare Advantage and Medicaid. The list of services that need prior authorization is generated from the same rules the requests are evaluated against. CRD returns “uncertain” rather than “no authorization needed” when it can’t decide.

Checked by: exchanges with the HL7 Da Vinci reference implementation, described on the prior authorization evidence and Da Vinci interoperability pages. Open: full DTR answer validation and package semantics, and an X12 278 bridge. On the 278, plans are currently relying on HHS enforcement discretion for FHIR-only prior authorization; confirm that position with your counsel.

Provider Directory

The directory is public, with no login, as CMS-9115-F has required since 2021, and it serves the nine Da Vinci Plan-Net 1.2.0 profiles. Internal content is stripped from the public route, and a plan publishes by being listed in the deployment’s directory configuration. Providers imported only as claim references are kept out of it.

Checked by: the Inferno Plan-Net kit. Open: the current kit is generated from Plan-Net 1.1.0, and its forward-chain searches are recorded as known kit issues.

04An access layer over legacy data

This is the blueprint’s most important idea and the hardest one to deliver: expose the data the plan already has without disrupting the system that holds it. For a Medicaid plan that system is usually QNXT, Facets, HealthEdge or a state-specific core, and it is not going anywhere before January.

Cloud Health Office takes the core’s data as CPCDS files, the Common Payer Consumer Data Set that CARIN Blue Button is built on. A plan drops claims, enrollment and coverage files on a schedule. Each import is idempotent, so re-sending a file does not duplicate claims, and a freshness report shows how current each tenant’s data is. The APIs above then serve that data, so the plan can see its own APIs running on its own data before the deadline.

Open: X12 837, 835 and 834 as a second source through the same pipeline is next. Getting a clean CPCDS export out of a given core is still per-plan mapping work; for QNXT we describe that on the QNXT adapter scoping page. There is no packaged adapter for any core.

05Provider EHR workflows

Electronic prior authorization only reduces burden when the provider’s EHR calls it at order time. Cloud Health Office serves CRD through CDS Hooks, DTR questionnaires and SMART app launch, and PAS for submission.

The honest limit

The other half of this item belongs to the EHR vendors and to each provider’s configuration. A payer cannot finish it alone, and neither can we. What a plan can do is publish working endpoints early and give its high-volume provider groups a test path. That is why provider engagement sits in the governance row below.

06Consent, identity, audit and privacy

The blueprint treats these as design requirements, and the code does too. Provider Access opt-out and Payer-to-Payer opt-in are recorded consents, not flags. System callers authenticate with SMART Backend Services signed assertions, and a Payer-to-Payer caller is bound to its own registered payer, not to whatever the request body claims. Tenants are isolated per plan. Every Patient Access disclosure is written to a ledger. The source is available under BSL 1.1, so a plan’s security team can read exactly what the software does before it is deployed.

Open: member-facing notices, consent screens and representative or confidential-address handling are the plan’s to author and approve.

07Cloud infrastructure

Cloud Health Office runs on Kubernetes in a tenant dedicated to each plan, in the plan’s own cloud or operated for it by engagement. It is tested on Google Kubernetes Engine and on local Kubernetes. The public scale evidence is the Million Claim Challenge: 1,000,000 deterministic synthetic claims on local Docker Desktop Kubernetes at 155.89 claims per second with zero dead letters. That is local engineering evidence, not a production-cloud capacity claim.

08Governance and change management

Every serious version of the blueprint says the technology is the smaller part: executive sponsorship, provider engagement, member education and privacy review decide whether the APIs are used. That is right, and it is yours. No vendor can supply a plan’s executive sponsor.

What we can do is shorten the technical side so the plan’s attention goes where it should. Professional Services can help with architecture, scoping and implementation. A health plan does not need to purchase or deploy Cloud Health Office in order to engage Professional Services. Cloud Health Office technology is recommended only where appropriate.

09Metrics

The prior authorization metrics CMS-0057-F requires plans to publish are computed: approval and denial rates for standard and expedited requests, approvals after appeal, extended-then-approved, and mean and median time to decision. Complete public publication is still to do.

The blueprint also suggests tracking outcomes such as duplicate tests, staff time, readmissions and care gaps. Cloud Health Office does not measure those today, and we would rather say so than imply it.

10Check your own APIs against it

Most Medicaid plans will meet the January 1, 2027 date with whatever their current vendors deliver. The useful question is whether those APIs will pass the tests app developers, providers and other payers will run against them.

A CMS-0057-F conformance check answers that. We run the same Inferno kits described above (US Core, CARIN for Blue Button, Bulk Data with SMART Backend Services, and Da Vinci Plan-Net) against your sandbox or test endpoints, with no PHI, and review prior authorization and CMS metrics against a checklist. It takes four weeks for a fixed fee, and you get the findings and why each one failed. If you then want the gaps closed, Cloud Health Office can run the fixes in a tenant your plan controls, beside your current core.

A blueprint tells you what to build. A conformance check tells you whether what you built works. The second is cheaper to find out in November than in January.
