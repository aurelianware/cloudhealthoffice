Payers running QNXT, Facets, HealthEdge, or another core administrative processing system (CAPS) all face the same practical question: how do you implement modern FHIR interoperability and prior authorization when decades of membership, benefits, provider, authorization, and claims processing already live in existing systems? The interoperability requirement is new. The book of business is not.

There are, broadly, three architectural options:

  • Force the legacy core to implement every new interoperability capability. This turns each new FHIR API and prior-authorization workflow into a core-vendor roadmap item, on the core vendor’s timeline and at the core vendor’s price.
  • Replace the core entirely. A full rip-and-replace carries the highest cost and the highest operational risk, and it front-loads that risk before any interoperability value is delivered.
  • Deploy CloudHealthOffice alongside the existing core and progressively move capabilities into it when—and only when—doing so is appropriate.

CloudHealthOffice (CHO) supports both ends of that spectrum. It can operate as a modern interoperability layer around an existing core, and it can operate as the payer core backend itself. The same FHIR boundary serves both, which is what lets a plan start small and modernize on its own schedule.

The CMS-0057-F interoperability boundary

CMS-0057-F—the Advancing Interoperability and Improving Prior Authorization Processes final rule—requires impacted payers to implement modern interoperability APIs, including Prior Authorization API capabilities, on a standardized FHIR R4 foundation. That is the requirement CHO is built to help satisfy: standardized FHIR APIs that a plan can operate without re-platforming everything behind them.

It is worth being precise about the building blocks. CRD (Coverage Requirements Discovery), DTR (Documentation Templates and Rules), and PAS (Prior Authorization Support) are recommended Da Vinci implementation approaches that support the required Prior Authorization API capabilities. They are widely used industry patterns, and they are how CHO implements the workflow—but the current final rule does not individually mandate CRD, DTR, and PAS by name. Describing them as the rule’s named mandates would overstate the regulation. What the rule asks for is the capability; CRD, DTR, and PAS are a well-established way to deliver it.

Language we use deliberately: “PAS-aligned,” “CRD capability,” “DTR capability,” and “CMS-0057-F readiness.” We avoid “CMS certified” or “guaranteed compliant,” because production compliance is a property of a payer’s whole deployment, not of any single piece of software.

For the regulatory text itself, the CMS-0057-F Readiness page collects the authoritative CMS and HL7 references—the Federal Register final rule, FHIR R4 and US Core, and the HL7 Da Vinci implementation guides—alongside how the readiness surface maps to them.

CRD: what does the payer require?

Coverage Requirements Discovery answers a question at the moment of ordering: for this patient and this service, what does the payer require? A provider working in an EHR selects or signs an order, and the EHR calls the payer through CDS Hooks. The payer evaluates the draft order against the member’s coverage and answers with actionable guidance—taking into account eligibility, plan, benefits, provider, procedure, diagnosis, place of service, policy, and authorization requirements.

In CHO this is a running service, not a diagram. The CRD controller exposes the CDS Hooks discovery endpoint (publicly, per the CDS Hooks 2.0 spec) and advertises two hooks—order-select and order-sign. When an EHR invokes a hook, the CRD service:

  • extracts the coded content from the draft orders (for example, ServiceRequest.code and MedicationRequest.medication);
  • invokes terminology translation where appropriate—SNOMED CT codes are translated toward billing/classification systems before evaluation;
  • calls the CHO Prior Authorization Rule Engine to evaluate each code against payer-specific rules;
  • falls back to payer-specific code classifications (auth-required, documentation-required, auto-approved) when the rule engine has nothing dispositive to say;
  • returns CDS cards describing the outcome—prior authorization required, no authorization required, or additional documentation required, with a suggestion to launch DTR when documentation is needed.

This is deliberately concrete: the CRD implementation reads real codes out of the order, actually calls the terminology service, and actually calls the rule engine before it builds a card. The classifications and rules it evaluates against are payer-configured—which is exactly where onboarding does its work.

Terminology: making every code speak the same language

Terminology is not a side quest in this workflow—it is load-bearing. Providers order in the vocabulary their EHR uses; payers adjudicate in the vocabulary their policies use. Between the two sit SNOMED CT, CPT, HCPCS, ICD-10-CM, LOINC where appropriate, and payer-specific code groupings. If a code isn’t normalized before it reaches a rule, the rule is evaluating the wrong thing.

CHO provides FHIR-native terminology capabilities—CodeSystem, ValueSet, and ConceptMap—including ConceptMap/$translate and a batch translate operation used inside the request path. Crucially, the CRD implementation actually calls the terminology service: when a draft order carries SNOMED CT, CRD posts those codes to the terminology service for translation toward ICD-10-CM before classification, and degrades gracefully to the raw codes if terminology is briefly unavailable. Terminology is in the hot path, not a document sitting beside it.

DTR: what information does the provider need to supply?

When CRD determines that documentation is required, DTR answers the next question: what information does the provider need to supply, and in what structured form? Documentation Templates and Rules use FHIR Questionnaire and QuestionnaireResponse to gather exactly what a policy requires, inside the clinical workflow.

The DTR controller implements this as tenant-aware, patient-contextual FHIR:

  • Questionnaire GET, search, create, and update;
  • QuestionnaireResponse GET, search, and submit (accepting only completed or amended responses, validated against an existing questionnaire and a patient subject);
  • the $questionnaire-package operation that assembles a questionnaire with its dependencies for a patient context.

That is a genuine, working DTR surface. What it is not is a pre-written body of medical policy. The DTR machinery is generic; the content that flows through it is payer-specific and determined during onboarding—questionnaire content, medical-policy content, prepopulation rules, clinical governance, and effective dates all belong to the plan. CHO provides the templates-and-rules engine and the FHIR contract; it does not ship a turnkey payer DTR implementation that works without configuration.

PAS: submit the authorization and receive the decision

Prior Authorization Support closes the loop: submit the authorization and receive the decision. The PAS controller implements the synchronous Claim/$submit operation, aligned to the Da Vinci PAS implementation guide, and it does real payer business processing along the way rather than proxying a FHIR bundle into some other platform.

On each submission, PAS:

  • validates and extracts the PAS Claim from the request bundle—bounding bundle size, rejecting unexpected resource types, and requiring relative FHIR references (which also closes an SSRF vector before any reference is forwarded internally);
  • runs CMS-0057-F-oriented compliance checks on the claim and rejects non-compliant submissions with a clear reason;
  • performs a provider-verification pre-check—an excluded provider NPI is auto-denied with a PROVIDER_EXCLUDED reason and its exclusion source;
  • auto-adjudicates within a response-time budget and returns an approved, denied, or pended decision;
  • persists the resulting authorization and records telemetry and metrics (decision, firing rule, and duration) for every submission.

The distinction matters. A pass-through would hand the bundle off and report back whatever another system said. PAS in CHO validates, screens the provider, decides, and persists—payer business processing, expressed as FHIR.

Architecture: the boundary in front, the systems behind

Put CRD, DTR, and PAS together and they are not three isolated APIs—they are one connected payer workflow. CRD discovers what is required, DTR collects what is needed, PAS submits and decides, and the decision is written to the Authorization Service, all on CHO services.

In the first end state, CHO sits between the provider/EHR and the payer’s existing systems. Above the line it exposes CRD, terminology, the Prior Authorization Rule Engine, DTR, PAS, the Authorization Service, SMART/OAuth, provider verification, and audit/metrics. Below the line, a payer-specific adapter layer connects to QNXT, Facets, HealthEdge, a utilization-management system, or whatever else is the real source of truth. The provider sees one modern FHIR boundary; the payer keeps its systems of record.

In the alternate end state, the same boundary sits in front of CHO itself as the core backend—FHIR, membership, eligibility, benefits, providers, prior authorization, claims, accumulators, and payer administration all running on CHO. The external FHIR contract is identical. That identical contract is the whole point: it is what lets a payer change what is behind the boundary without changing what providers integrate against.

Payer-specific adapters, not universal adapters

It is tempting to claim a single, preconfigured QNXT adapter, a universal Facets adapter, or a plug-and-play HealthEdge integration. We deliberately don’t, because it wouldn’t be true. Two payers running the same CAPS product can differ in almost every way that matters to an integration:

  • product versions, enabled modules, and local extensions;
  • available APIs and middleware;
  • data warehouses, UM systems, and provider systems;
  • which team operationally owns which domain.

So the adapter is decided during onboarding, not assumed. Onboarding determines:

The QNXT, Facets, and HealthEdge adapters are implementation and onboarding integrations—not universal preconfigured adapters.

Progressive core modernization: three deployment models

Because the FHIR boundary stays constant, a payer can choose how far behind it to modernize—and change that choice over time.

Model 1

CHO beside the core

CloudHealthOffice handles FHIR, CRD, DTR, PAS, terminology, and modern payer services, while QNXT, Facets, or HealthEdge remains authoritative for existing core domains.

Model 2

Hybrid modernization

Selected payer capabilities move into CHO over time—for example prior authorization, provider verification, benefit services, eligibility, provider administration, and claims—while the legacy core keeps the rest.

Model 3

CHO as the core

CloudHealthOffice becomes the payer backend and the old core is retired—membership, eligibility, benefits, providers, prior authorization, claims, and accumulators all run on CHO.

The key positioning point: a payer can start with Model 1 and progressively reach Model 3 without changing the external FHIR contract. Modernize incrementally; keep the boundary stable.

What this does not claim

Everything above is implemented technical capability—CRD, DTR, and PAS capabilities that are PAS-aligned and Da Vinci-shaped, wired to a terminology service and a rule engine. None of it is a regulatory certification, and none of it makes a payer compliant on its own. Production CMS-0057-F compliance depends on the payer’s configuration, identity, source systems, policies, data quality, operations, security controls, governance, and legal and compliance review. CHO supports an implementation strategy for CMS-0057-F readiness; it does not replace the payer’s responsibility for it.

That is also why the honest positioning is the strong one. A plan does not have to bet its core on an interoperability deadline. It can stand up a compliant-shaped FHIR boundary now, keep its systems of record, and decide later—domain by domain—how much of the core to modernize.
