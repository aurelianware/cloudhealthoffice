CMS-0057-F & Payer Modernization

What a Conformance Test Kit Proves, and What It Doesn’t

A test suite you wrote, run against fixtures you wrote, shares every misreading of the specification that you have. Someone else’s tests do not. This is how Cloud Health Office runs ONC’s Inferno kits against its own APIs — and what those kits can and cannot settle.

Series: CMS-0057-F & Payer Modernization Published: October 23, 2026 For: Payer architects, compliance leads & vendor management

Cloud Health Office has somewhere north of twelve thousand of its own automated tests. Not one of them can tell us whether we have read the specification correctly, because every one of them was written by the same people who read it.

That is the gap a conformance test kit fills, and it is why we run them. It is also why this page exists: the kits are easy to misrepresent, and “we run Inferno” is the kind of sentence that sounds like a certification and is not one.

State of play, 23 October 2026

No Inferno kit has yet produced a verdict on Cloud Health Office, in any suite. Two suites are wired and execute; three more are defined and not yet executed. The harness only became able to run a kit end to end this week. When the first results exist they will be published, and the first of them should be expected to be findings rather than a pass.

01What Inferno actually is

Inferno is an open-source FHIR conformance test harness built under the Office of the National Coordinator. It runs as a service, drives your API the way a real client would, and reports findings against the published Implementation Guide — requirement by requirement, not as a single pass or fail.

The important properties, for a payer evaluating any vendor: it is free, it is public, and you can run it yourself. A health plan does not have to take its vendor’s word about FHIR conformance. It can point a kit at a vendor’s sandbox and read the findings directly.

One clarification worth making early, because the adjacency invites confusion. Inferno is ONC’s tool. Running an ONC tool is not ONC approval, endorsement, or certification of anything, and nobody — us included — should write it as though it were.

02Why run somebody else’s tests

Here is the problem with a large internal test suite. Suppose we misread a profile requirement — we believe a particular element is optional when the Implementation Guide makes it mandatory. We then write the code to match our reading, and we write the test to match our reading. The test passes. It will keep passing forever. The suite has confirmed our interpretation to us, which is not the same as confirming it.

This is the same argument we make elsewhere about reference implementations: our Da Vinci interoperability evidence exists because exchanging messages with software written by somebody else tests something our own fixtures structurally cannot. A conformance kit applies that idea to profile conformance instead of workflow. The kit encodes a third party’s reading of the specification. Where their reading and ours differ, the kit says so.

Internal tests prove the code does what we intended. Conformance kits test whether what we intended was right. A platform needs both, and they are not substitutes.

03How we run them

The harness starts a kit and a Cloud Health Office instance together on an isolated network, seeds synthetic data, and points the kit at the running service. It refuses to start a kit if seeding fails, and it checks that Cloud Health Office answers its own metadata endpoint before any suite begins — because a kit that cannot reach the system under test reports that identically to a system failing every single requirement, and those two results mean completely different things.

Two suites are wired and execute today:

  • US Core 3.1.1 — capability statement, Patient, Encounter.
  • CARIN Blue Button, the c4bb_v200 financial groups — capability statement, Patient, Coverage, ExplanationOfBenefit, Organization, Practitioner.

Three more are defined and not yet executed: a DTR payer-server suite, a PDex server suite, and a PDex client suite. The whole inventory lives in interop/scenarios.json in the public repository, so the list of what we claim to exercise is itself reviewable.

A word we are careful with

In that inventory file, implemented: true means the harness executes the scenario — not that a result exists, and certainly not that it passed. Two scenarios are implemented and awaiting a first real run. Three are defined and not executed. No kit has judged this platform in any suite. The distance between “wired up” and “passing” is exactly the distance this page is trying not to let anyone cross by accident.

04Pinned, because a verdict that drifts is not a verdict

Every kit is pinned to an exact release, recorded with its commit hash, and every supporting container image is pinned by digest. A test in the build fails if any image reference floats.

That is not process for its own sake. Kit releases change: a new version of a test kit has newly failed systems that previously passed, because the kit’s own reading of the specification was corrected. If we ran an unpinned kit, a published result could change meaning with no corresponding change to our code and no reviewable diff explaining why. The pins, each with its source commit, are in interop/versions.json:

v1.1.6US Core test kit
v0.16.3CARIN for Blue Button test kit
v0.17.1Da Vinci DTR test kit
v0.13.2Da Vinci PDex test kit

The same file pins the HL7 FHIR validator at 7.0.3 and the Da Vinci reference implementations the interoperability harness exchanges messages with. Moving any pin is a reviewed change, which means the question “why did this result change?” always has an answer in version control.

05The suite that cannot grade us

This is the part we would quietly leave out if the goal were to look good, so it is the part worth reading.

CMS-0057-F’s Provider Access API carries claims and encounters as non-financial CARIN Blue Button ExplanationOfBenefit resources — the same record as a claim, without the money. Cloud Health Office declares the CARIN Blue Button 2.2.0 -Basis profiles for these, which is what the current Implementation Guide and the Da Vinci Provider Access guidance call for.

The CARIN kit at v0.16.3 contains a non-financial suite, c4bb_v200devnonfinancial. It checks the older -NonFinancial profile canonicals, from an April 2023 snapshot of that branch which the kit bundles. Different canonical URLs. The suite therefore matches nothing we serve — not a pass and not a failure, in either direction. Pointed at our Provider Access API it would report a wall of findings that say nothing about whether our resources are conformant.

The decision, and why

We could make that suite go green tomorrow by renaming our profiles to the -NonFinancial canonicals. We did not, and will not. That would turn a test green by making the platform wrong against the current Implementation Guide, in favour of a superseded draft. The suite is recorded as defined-and-not-run, with this as the stated reason, until a kit release regenerated against CARIN Blue Button 2.2.0 exists.

There is a general lesson in it for anyone buying payer software on the strength of test results. A test kit is a piece of software with a version, written against a specification that moves. “Passes the kit” and “conforms to the guide” are different claims, and they can come apart in either direction. When they do, the guide is the thing that matters.

06What a pass would, and would not, mean

Suppose every wired suite comes back clean. Here is precisely what a payer would be entitled to conclude:

What it would establish

That the API satisfied the requirements that kit version encodes, at a named revision of our source, against synthetic data, for the resources and interactions in those specific suite groups.

What it would not establish

Not certification. No scenario status and no kit result constitutes certification by CMS, ONC, HL7, or anyone else.

Not production validation. All of our test data is synthetic. No exchange described anywhere on this site has moved production member data.

Not completeness. A kit proves the requirements it encodes, in the groups that were run — not the whole of an Implementation Guide, and not the whole of CMS-0057-F.

Not payer rule parity. Two plans can pass every conformance suite there is and still reach different coverage decisions on the same request, because conformance is about the shape of the conversation and not the content of the rules.

We keep these results in a deliberately separate vocabulary from our own acceptance evidence, and from our Da Vinci interoperability evidence, and from offline profile validation. Four different questions, four different answers, never summed into one number. The Evidence Hub explains how they fit together and what each one does not claim.

07The green that wasn’t

Until this week, the nightly job that was supposed to be running these kits reported success every night while running nothing at all.

Two things were wrong at once. The job carried continue-on-error: true, so the workflow reported success even though the job’s own conclusion was failure. Underneath that, the kit profiles started a single container, where the upstream kits’ own compose definition runs five — the web application, a Sidekiq worker that actually executes queued test runs, a Redis instance behind that queue, and an HL7 validator service whose output is the suite’s verdict. With no writable data directory for its database, the one container we did start died on boot with a SQLite error before serving a single request.

So the dashboard was green, the kits were dead, and nothing was being tested. Fixed on 23 October 2026: the profiles now start the four load-bearing services, each sidecar is pinned by digest with a health check the kit waits on, and log capture covers every running container rather than only the ones a scenario names — because when an Inferno run goes wrong, the sentence explaining why is usually in the worker or the validator, neither of which the scenario names.

A green check mark is a claim like any other, and it deserves the same scrutiny as the claims it is supposed to support. Ours was wrong for a period. The diff that fixed it is public, which is the only reason this paragraph is worth more than it costs.

08Where this leaves us

Two suites wired and able to run, for the first time, as of this week. Three defined and not executed. One that cannot grade us at all until its upstream catches up with the Implementation Guide. And no verdict on Cloud Health Office from any conformance kit, which is a sentence we would rather publish now than explain later.

The requirement-by-requirement position on CMS-0057-F is maintained in the ePA gap matrix in the public repository, which is the source of truth and is deliberately harsher than any marketing page. The executable evidence that does exist today is in the Evidence Hub. When a kit produces its first real findings, they will appear there too, whatever they say.
