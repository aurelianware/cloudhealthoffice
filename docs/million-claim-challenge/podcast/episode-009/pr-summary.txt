## PR #946 - provider-aware prior-authorization validation

- Passed the claim provider NPI through claims-service prior-authorization validation.
- Authorization-service now rejects authorizations when the claim provider is not the provider approved on the authorization.
- Moved `PriorAuthRequired_WrongProvider` into scoreable MCC prior-auth evidence and seeded a distinct authorized-provider fixture for that scenario.
- Updated MCC, claims-service, and authorization-service tests for the provider-aware validation path.

## PR #947 - behavioral-health carve-out scoring

- Made the behavioral-health carve-out scenario scoreable as a CARC 96 non-covered-service denial.
- Normalized generated carve-out claims into a deterministic psychotherapy claim against the validation plan.
- Updated generator and validator tests so the scenario is no longer treated as unsupported.

## PR #949 - tenant-scoped behavioral-health service-category mapping

- Seeded a deliberately narrow, tenant-scoped MCC behavioral-health service-category mapping (CPT 90785-90899) during validator reference seeding, after a broad mapping attempt polluted tenant-default service categories and regressed unrelated scoring.
- Enabled the local Kubernetes run script to pass a deterministic seed and turn on the service-category admin write gate.
- Persisted service-category procedure-code rule IDs as BSON-safe strings in Mongo with a round-trip regression test.
- Temporarily marked behavioral-health carve-in/parity paid edge cases as unsupported - honestly - because the new mapping routed them to a behavioral-health category with no configured benefit, so they denied CARC 96 instead of paying.
- Scoped MCC provider network IDs by tenant so fresh tenants do not collide on shared Mongo IDs.

## PR #950 - enforcement-probed wrong-provider scoring and behavioral-health benefit completion

- Gated `PriorAuthRequired_WrongProvider` scoring behind a runtime probe that confirms the deployed authorization-service actually rejects wrong-provider authorization use, instead of assuming support from repository code.
- Added the missing behavioral-health benefit category to the MCC validation plan so `BehavioralHealthCarveIn` and `BehavioralHealthParityCheck` pay deterministically through a real behavioral-health benefit, and removed their temporary unsupported gate.

## PR #954 - plan-specific service-category overrides (found during confirmation)

- A first 100K confirmation attempt on #950 alone regressed to 7,178/13,000 matched (vs. 11,854/13,000 at Part 8), caused by a pre-existing, unrelated tenant-default service-category mapping bundle on the `demo` tenant shadowing the validation plan's numeric categories in the resolver's tenant-default lookup.
- Also surfaced a #950 self-collision: adding a covered behavioral-health benefit made `BehavioralHealthCarveOut` pay instead of deny, since it shares a CPT code family with carve-in/parity-check.
- Fixed both by seeding plan-specific `ServiceCategoryMapping` overrides scoped to the validation plan (plan-specific mappings win over tenant defaults in the resolver), and by tagging the carve-out claim with a synthetic modifier so a second, deliberately uncovered plan override intercepts only that claim.
- Also required: rebuilding `claims-service`, `benefit-plan-service`, and `authorization-service` from current `main` before either confirmation attempt - the long-lived local cluster predated #946's authorization-service provider-enforcement check.

## PR #956 - self-healing provider network-participation writes (found chasing the #954 follow-up)

- The 32 mismatches recorded as follow-up debt after the post-#950/#954 confirmation run (below) were not a COB bug. `EnsureProviderNetworkParticipationAsync` treated any `409` from `POST {id}/network-participations` as "already participates" and moved on.
- Provider-service actually rejects that write whenever the target provider is Active - mutations require an amend-to-Draft-then-activate flow - and no endpoint existed to populate an amended Draft's contents before activating it. Providers that went Active before #949 introduced tenant-scoped network IDs could never receive the new network-scoped participation.
- `NetworkCredentialingStage`'s `FailClosed` default then correctly denied claims against a network those providers were never actually registered under, and COB claims lost their otherwise-correct Pend outcome to that unrelated Deny (Deny outranks Pend in adjudication precedence).
- Fixed by making `AddNetworkParticipation` self-healing: an Active provider is auto-amended into a Draft, edited, and activated within the same call. Also fixed an incidental repo-wide `Microsoft.Azure.Cosmos` version split (3.61.0/3.62.0 across 28 projects) discovered while rebuilding services to test this.

## PR #958 - self-healing provider integrity-field correction (found in the #956 re-confirmation)

- The #956 re-confirmation run came back with COB fully clean but a new, unrelated regression: `ExcludedProviderDenied` 1,936/2,000. Same shape of bug, different surface.
- `MccProviderFixturePool.BuildRunScopedNpi` mints run-scoped provider NPIs from a value space that isn't infinite; this long-lived local cluster had accumulated enough providers across many prior runs that a fresh NPI collided with a provider created weeks earlier for an unrelated purpose. Seeding saw "already exists" and never verified the existing record's exclusion fields.
- The adjudication-path integrity gate reads `Provider.IntegrityScore`/`IntegrityRating` directly from provider-service as its source of truth, not `CredentialingStatus` - so the collided provider's stale "Clear" rating meant a claim that should have denied on exclusion paid instead.
- Fixed by adding `EnsureProviderExclusionAsync`, which verifies and corrects the existing record's integrity fields on every excluded-provider fixture claim, extending #956's self-healing amend pattern to provider-service's general `UpdateProvider` endpoint.
