## Fix history

The first 100K attempt against #950 alone produced 7,178/13,000 matched (5,036 mismatched) — worse than the Part 8 baseline (11,854/13,000), not better. Root-caused to two issues, both fixed by PR #954 (`mcc-plan-specific-service-category-overrides`):

1. **Pre-existing tenant-data conflict, unrelated to #950's own logic.** The `demo` tenant already had BP 5.6 system-default service-category mappings applied (descriptive string categories like `"Office Visit"`), seeded at some earlier point outside any MCC PR. These shadowed the validation plan's numeric benefit categories (`"98"`/`"73"`/`"48"`) in the resolver's tenant-default lookup, misrouting most claims — including simple `CleanProfessionalPaid` — to CARC 96 "no benefit configured" denials. Fixed by seeding plan-specific `ServiceCategoryMapping` overrides scoped to the validation plan itself; plan-specific mappings take precedence over tenant defaults in the resolver (`docs/architecture/service-category-mapping.md`), so the validator is now immune to whatever else is seeded on the tenant.
2. **Regression introduced by #950 itself.** Adding a covered Behavioral Health benefit to the validation plan (to fix `BehavioralHealthCarveIn`/`ParityCheck`) broke `BehavioralHealthCarveOut`, since it draws from the same CPT code family and started resolving to the same now-covered category instead of denying. Fixed by tagging the forced carve-out claim line with a synthetic modifier and adding a second, more-specific, deliberately-uncovered plan override that intercepts only that claim.

Also required for this run: `claims-service`, `benefit-plan-service`, and `authorization-service` were rebuilt from current `main` before either attempt — the cluster's long-lived images predated #946's authorization-service provider-enforcement check and claims-service's pend-observation telemetry (#936, #941), which would have produced false "not enforced" / incomplete pend results otherwise.
