Create a 10-12 minute two-host engineering podcast episode titled "Zero Unsupported, Then the Parallelism Nobody Profiled."

Use Alex and Jordan as experienced healthcare platform engineers. Make the discussion natural, analytical, and candid rather than reading the article aloud. This episode has two genuinely separate stories -- treat them as two acts, not one blended narrative.

## Act one: closing the sweep

Since Part 9, five synthetic scenario families in the benchmark corpus had never been scoreable -- generated, adjudicated, but with no logic to check whether the result was correct, so they were excluded from scoring and reported as "unsupported." Walk through the research step first: before writing any code, an investigation read the actual pipeline to figure out which of the five was most tractable, and found real differences in difficulty -- RetroEligibilityCoverageChange could reuse infrastructure Part 9 already built for a sibling scenario; the three subrogation variants had zero real signal to key off; MedicaidSpendDown needed a genuinely new benefit concept.

Cover each conversion concretely, not just "it's fixed now":

RetroEligibilityCoverageChange models a real administrative event -- a benefit-plan correction recorded today, effective retroactively two weeks ago. A new field on the real member-service Member model, not a benchmark fixture, plus a pipeline check that pends any claim whose service date falls in that retroactive window. 26 of 26 matched.

The three subrogation scenarios turned out to be one fix, not three -- real claims carry an X12 837 related-causes code (auto accident, employment, other accident) signaling a third party might owe money first, and the platform had never modeled that field at all. One new field, one check, three scenarios converted for the price of one. Make the point directly: converting all three once the shared mechanism was clear was the right call, not scope creep -- leaving two nearly-free conversions unsupported after building the capability would have been arbitrary.

MedicaidSpendDown was the one that actually needed something new -- a "medically needy" eligibility category where a member must incur enough medical expense in a budget period before Medicaid activates. Modeled as a member-level eligibility fact, deliberately kept separate from the production deductible/accumulator engine, since spend-down gates whether coverage applies at all, not how much of it remains.

Land the milestone clearly: workflow checks 1,300 of 1,300 matched, zero unsupported, the first time this series has ever run with no unsupported claims at all.

Then tell the CI story honestly, because it's a real process lesson, not a footnote: two tests broke on GitHub Actions, not because the new code was wrong, but because those tests had used one of the now-converted scenarios as their working example of "an unsupported case" -- their premise went stale, not their target. The actual gap: the test project containing them hadn't been included in local test runs during this work, only two of the three relevant test projects had been checked before pushing. CI caught what local discipline missed. State plainly that this was a real process gap, not spin it as CI "working as intended" -- the goal is running the full test surface locally next time, not leaning on CI as the safety net by default.

## Act two: a dashboard read carefully

Pivot clearly -- this is a different investigation, prompted by an informal observation, not a hypothesis someone set out to test. Watching the mass-adjudication dashboard across unrelated verification runs, parallelism-20 runs visibly looked faster than parallelism-56 runs. Instead of trusting the impression, the dashboard's own API got queried directly for the last 25 runs across every parallelism level tested this series. The pattern was real and stranger than expected: P56's best throughput run was worse than P20's best throughput run on both latency and throughput at once -- not a normal tradeoff curve, the signature of contention, something shared getting saturated well below 56 concurrent workers.

Walk through the diagnosis using the same technique this series has used twice before (Part 10 on claims-service, Part 12 on MongoDB): live cgroup cpu.stat, before and after an identical controlled load test, checked across every candidate service. The leading suspect going in was Redis, backing the accumulator cache -- and it showed zero throttling, completely exonerated. The real answer: member-service, a single replica on half a CPU core, doing a member lookup for literally every claim in the pipeline, throttled 48 percent of the time it ran. Coverage-service, serving every COB scenario, showed the same shape at a smaller scale. Neither had been touched by any of this series' three prior CPU-limit rounds, because neither had ever been the bottleneck before -- they'd simply never been tested at this concurrency until now.

Cover the fix and its immediate consequence as one connected story, because that's what actually happened: raising member-service and coverage-service's CPU limits fixed the throttling and improved throughput and latency -- and immediately exposed a second bottleneck. Once the pipeline could sustain real concurrent load instead of queuing behind member-service, claims-service got OOM-killed mid-run. Plenty of CPU, not enough memory headroom. Raised that too. Final verified result: 363 claims per second, P95 269 milliseconds -- the best-performing configuration at any parallelism level tested this entire session, from 10 through 56. Parallelism 56 was never inherently worse. It had just never been given enough to work with.

## Two things to name honestly, not smooth over

First: applying the actual committed Kubernetes manifests for the first time in this cluster's three-week local history -- necessary just to test the CPU change -- reset live, hand-patched configuration back to what was checked into the repository, which didn't match reality. The running pods were quietly in Development mode with working database credentials; the file said Production mode with a placeholder password. Both services crash-looped until the real values were restored by hand. Frame this precisely: not a code defect, a reminder that a manifest nobody re-applies for weeks isn't actually validated by sitting correctly in the repository.

Second: the fix's own verification run produced 77 real mismatches, and it would have been easy to blame the OOM kill for them. Investigate on air the way it was actually investigated -- pulled the specific mismatched claims from the dashboard's per-claim endpoint, found they were all the identical scenario with the identical wrong-outcome pattern, and traced it to a completely different, already-disclosed gap from Part 12: member seeding never updates an existing record, it just skips silently on conflict. Running several overlapping-seed jobs back to back during this investigation caused real collisions. Say clearly that this wasn't a defect in the scenario conversion itself -- its own dedicated verification, run cleanly, scored 26 of 26 -- it was an artifact of how the investigation itself was run, and the underlying gap remains open.

Close by tying the two acts together: one closed a scoring gap this series has carried since Part 9; the other found a real performance ceiling that had been sitting in plain sight in the dashboard the entire time, waiting for someone to read it carefully instead of assuming higher concurrency should always mean more throughput.
