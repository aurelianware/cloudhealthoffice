Create a 10-12 minute two-host engineering podcast episode titled "One Million Claims, and the Bug Only That Scale Could Find."

Use Alex and Jordan as experienced healthcare platform engineers. Make the discussion natural, analytical, and candid rather than reading the article aloud.

Open by naming what makes this episode different from every one before it: since Part 6, every single episode has closed with the same recurring section, "the road to one million" -- and every one of those episodes has been building toward a number that had never actually been attempted. This is the episode where it finally ran. Frame it honestly: Part 14 had just closed the last known gap (zero unsupported scenarios) and fixed the last known performance ceiling (parallelism 56), both verified at 20,000-claim scale -- and nothing left disclosed as open pointed at a reason not to try the real target. Mention the care taken before attempting it: every touched service rebuilt fresh from the actual merged code rather than reusing ad-hoc images, and a deliberately fresh random seed chosen specifically to avoid a pollution mechanism the previous episode had just finished diagnosing.

Walk through the first attempt with real numbers, not vague description: 999,977 of 1,000,000 claims processed, zero unsupported, 129,989 of 130,000 scoreable checks matched, payment gate exact on all 20,000 comparisons, and the wall-clock-gap fix from Part 13 holding at fifty times the scale it had ever been tested at. Then the real news: 23 platform failures -- the first this series has seen since it started chasing every single one down instead of treating them as background noise. Make the shape of the failure the interesting part: all 23 appeared in one tight window, between the 950,000 and 960,000-claim mark, and nowhere else in the run. Before that point, zero. That specific shape -- fine, then abruptly and completely wrong, late in a very long run -- is itself a clue, and the investigation should be told as reading that clue, not as randomly guessing at services to check.

Cover the diagnosis as a real investigation with a false start ruled out cleanly: the obvious first suspect was concurrency, another parallelism-56-shaped contention problem like Part 14 just fixed. It didn't survive contact with the data -- Redis had shown zero CPU throttling in every test this series has ever run against it. Not a CPU story. The real signal came from two direct checks: `used_memory` sitting pinned exactly at a 768-megabyte ceiling, not near it, exactly at it; and `evicted_keys` reading over six million, more evictions than the store even currently held. Explain plainly, for a technical but not necessarily Redis-expert audience, why that specific combination is diagnostic: under the `volatile-lru` eviction policy, hitting the memory ceiling doesn't fail a write, it forces an eviction scan to make room first, on every single write, for as long as the store stays full -- and that scan overhead, on a single-threaded command processor, under real concurrent load, is exactly what turns a normal sub-millisecond read into a 22-second wait. Explain why this scale specifically triggered it: a full million-claim run touches roughly 962,000 distinct member accumulators, an order of magnitude past what any smaller verification run had ever built up.

Land the reveal about where that 768-megabyte number actually came from, because it's the sharpest point in the episode: it didn't exist anywhere in the committed Kubernetes manifest. The checked-in file specified no memory limit at all -- default, unconfigured Redis. The number only existed as a hand-applied patch on the live cluster, from some point in its three-week history, never synced back to the file that was supposed to describe it. Connect this directly and explicitly to Part 14's own finding of the same exact pattern on two other services days earlier -- state the throughline plainly: a Kubernetes manifest that nobody re-applies for weeks isn't actually validated by sitting correctly in a repository. It's validated by matching what's actually running, and this cluster had drifted from its own paperwork in at least three places now.

Cover the fix and its honest, complete verification: raised the ceiling from 768 megabytes to 3 gigabytes, roughly four times the actual measured working set, and for the first time wrote the real configuration into the manifest instead of leaving it as tribal knowledge. Re-ran the identical million-claim job, not a smaller stand-in, to check it. Redis used only 387 megabytes of the new ceiling, zero evictions the entire run. Platform failures: 23 down to zero. The wall-clock gap held again, down to 7 milliseconds unaccounted out of two and a half hours -- arguably the cleanest number this whole series has ever produced for that specific metric.

Then be precise and honest about what the fix did not solve, because pretending Redis explains everything would undercut the credibility of the entire investigation: throughput on the clean run was still only 123.81 claims per second, nowhere close to the 363 per second verified at 20,000-claim scale in the previous episode. State clearly that this was checked, not assumed -- Redis in the clean run used only 13 percent of its new capacity and evicted nothing, confirmed innocent a second time on two separate runs. Name the real remaining candidates without pretending to know which one it is: MongoDB under genuinely sustained multi-hour load in a way a short burst test can't recreate, connection-pool or garbage-collection pressure that only builds up over hours, or the more uncomfortable possibility that short-burst P95/P99 numbers were simply never a valid stand-in for real steady-state behavior at all. Explain the decision not to chase it further in this same episode: it doesn't touch correctness, doesn't block anything currently running, and closing it for real would mean deliberately reproducing a multi-hour condition rather than debugging something already in front of you.

Close by tying it to the entire series' pattern, because this episode is proof of the pattern working exactly as intended rather than an exception to it: every scale increase this series has ever attempted has found something the previous scale literally could not see -- Part 8 found the next bottleneck at 100,000, Part 10 found MongoDB's real cost at 250,000 hiding under a guessed one, Part 12 found the actual database ceiling at 500,000 only after two unrelated fixture bugs got out of the way. State the point directly: reaching one million didn't happen despite finding a new bug. It found a new bug specifically because it was the first time anything had actually reached that scale for real. That's the payoff of the whole "road to one million" refrain finally landing -- not a clean number, an honest one, with the fixes that came before it all holding at once, and one clearly named question left for whoever runs the next one.
