# Provider Identity & Versioning

Status: 5.1 — initial implementation
Service: `src/services/provider-service`

## Why

Claims, coverage, and audit consumers all need to answer "what did this
provider look like at the time of service?" — but until now the
provider service mutated `Provider` documents in place. Network
participation changes, suspensions, and terminations all collapsed onto
a single mutable row, and historical replay was impossible.

5.1 establishes an immutable, append-only version chain on each
provider, mirroring the plan-version chain shipped under capability 5.1
of the benefit-plan roadmap.

## Identity model

A *provider* is the abstract entity identified by `(TenantId, ProviderId)`.
Each *version* is a row in the `Providers` collection with a stable
`VersionId` (ULID, Crockford base-32, lexicographically sortable by
creation time) and a 1-based `VersionNumber` monotonic within the
`(TenantId, ProviderId)` chain.

```
Provider
├── Id                       per-version document id (Cosmos / Mongo _id)
├── TenantId                 partition key — multi-tenant isolation
├── ProviderId               chain key — stable across versions
├── VersionId                ULID — stable per-version identifier
├── VersionNumber            1-based monotonic
├── VersionState             Draft | Active | Suspended | Superseded | Terminated
├── PredecessorVersionId     null on the genesis version
├── ActivatedAt / ActivatedBy
├── SuspendedAt / SuspensionReason
├── SupersededAt / SupersededByVersionId
├── TerminationDate / TerminationReason   (existing fields, reused)
└── ... NPI, demographics, network participations, credentialing, ...
```

`Id` and `ProviderId` are distinct on purpose. Existing single-row
chains satisfy `ProviderId == Id` after hydration, so callers that have
historically used the document `Id` as the provider identifier
(claims-service `HttpProviderService`, coverage-service
`HttpProviderServiceClient`) continue to work unchanged. New chains
generated by `AmendActiveProviderAsync` allocate a fresh per-row `Id`
while preserving `ProviderId`.

## State machine

```
                  ┌──────────┐  activate  ┌────────┐  supersede   ┌────────────┐
   create draft → │  Draft   │ ─────────▶ │ Active │ ───────────▶ │ Superseded │
                  └──────────┘            └────────┘              └────────────┘
                       ▲                       │  ▲
                       │ amend                 │  │ reactivate
                       │                       ▼  │
                       │                  ┌──────────┐
                       └──────────────── │ Suspended │
                                         └──────────┘
                                              │ terminate
                                              ▼
                                      ┌─────────────┐
                                      │  Terminated │
                                      └─────────────┘
```

- **Draft** — mutable. Only `UpdateDraftAsync` may change it.
- **Active** — read-only at the application layer. The repository's
  `UpdateAsync` rejects writes against non-Draft rows with
  `ProviderVersionStateException` → controller maps to HTTP 409.
- **Suspended** — non-terminal pause; the same `VersionId` is mutated
  in place (state-only mutation via `ReplaceVersionRowAsync`). A
  Suspended head is reactivated via `ReactivateProviderAsync`, which
  creates a new Active version cloned from the suspended head, and
  marks the suspended row as `Superseded` (with a successor pointer).
- **Superseded** — displaced by a newer Active version. Still
  queryable by `VersionId`; downstream consumers that hold a stamped
  `VersionId` continue to see the exact bytes that were Active at the
  time of service.
- **Terminated** — permanently ended with no successor. Distinct from
  Superseded: `Terminated` requires a deliberate `ReactivateProvider`
  call to resume the chain (which creates a brand-new Active version
  cloned from the terminated head); `Superseded` is reached
  automatically when a new Active version is published.

Suspended → Terminated and Active → Terminated are both supported.
Terminated is terminal; reactivation is the only path forward.

## Lookup contracts

| Caller intent | Method |
| --- | --- |
| "Give me this version exactly" | `GetVersionAsync(providerId, versionId)` |
| "Give me whatever is current today" *(legacy callers)* | `GetByIdAsync(id)` — resolves chain key to head non-Draft version |
| "Give me the version effective at this date" | `GetLatestActiveAsync(providerId, asOf)` |
| "Show me the chain" | `ListVersionsAsync(providerId, pageSize, cont)` |

## Backward compatibility

The `Providers` collection contains pre-existing rows that lack
identity fields. Both repository implementations apply the same
hydration rule on read:

```
if (string.IsNullOrEmpty(provider.ProviderId)) {
    provider.ProviderId = provider.Id;
}

if (string.IsNullOrEmpty(provider.VersionId)) {
    provider.VersionId = provider.Id;
    provider.VersionNumber = 1;
    provider.VersionState = provider.Status switch {
        Terminated => Terminated,
        Inactive   => Suspended,
        Pending    => Draft,
        _          => Active
    };
}
```

Empty `VersionId` is the unambiguous legacy marker — every write since
this PR populates it. No data backfill is required.

The legacy `Provider.Status` enum (`Active|Inactive|Terminated|Pending`)
is preserved as the back-compat signal. Hydration normalizes `Status`
from `VersionState` (Active↔Active, Suspended→Inactive,
Terminated→Terminated, Superseded→Inactive, Draft→Pending) so existing
consumers — `coverage-service` `PcpAssignmentService` (which checks
`provider.Status == Active`), and the Mongo and Cosmos search filters
(`status = 'Active'`) — continue to work without changes. Callers do
not need to migrate to `VersionState`; they can if they want stronger
state assertions.

## Atomicity

`ActivateAndSupersedeAsync` flips the draft to Active and the
predecessor (if any) to Superseded in a single transaction:

- **Cosmos** — transactional batch on the `(TenantId)` partition key.
- **Mongo** — session transaction (requires a replica set). On
  single-node deployments we fall back to sequential writes and emit a
  warning log so ops can spot the split-state risk.

Repositories perform the writes; the service layer is responsible for
applying the new states and timestamps before calling.

`SuspendVersionAsync` and `TerminateVersionAsync` use
`ReplaceVersionRowAsync` for an in-place state-only mutation on the
single head row — no atomicity concerns because there is no successor
to update in the same transaction. Reactivation goes through the
same `ActivateAndSupersedeAsync` primitive used by amend → activate.

## Events

Five events complete the state-machine observability surface:

| Event | EventId | Emitted when |
| --- | --- | --- |
| `ProviderVersionActivated` | `activated:{versionId}` | A draft is moved to Active. |
| `ProviderVersionSuperseded` | `superseded:{from}->{to}` | A predecessor is flipped to Superseded by a new Active version. |
| `ProviderVersionSuspended` | `suspended:{versionId}` | An Active version is paused in place. |
| `ProviderVersionReactivated` | `reactivated:{versionId}` | A new Active version replaces a Suspended or Terminated head. |
| `ProviderVersionTerminated` | `terminated:{versionId}` | An Active or Suspended version is permanently terminated. |

Events live in the `ProviderVersionEvents` collection (Mongo). Envelope
mirrors `MemberEvent` and `PlanVersionEvent`: client-supplied `EventId`
for idempotency, monotonic `Version` per `(TenantId, ProviderId)`,
partition key `{TenantId}:{ProviderId}`, payload as a JSON object
(BSON-mirrored as a string).

Bus fan-out (claims-service, coverage-service notifications) is
intentionally not wired in this PR — `IProviderVersionEventPublisher`
is positioned for a decorator that adds bus publishing without
touching call sites. Cosmos-only deployments without the events stream
provisioned register a no-op publisher that warns on emit.

## Audit log

Every state transition appends a `ProviderTransition` row
(`ProviderTransitions` collection) with `from`/`to`/`type`/`reason`/
`actor` so audit consumers don't need to replay the event stream to
reconstruct history. Transition types: `Activate`, `Amend`,
`Supersede`, `Suspend`, `Reactivate`, `Terminate`.

## API surface

The `ProvidersController` carries two class-level `[Route]` attributes
so every action answers at both `api/Providers/...` (legacy, preserved
for existing claims-service / coverage-service consumers) and
`api/v1/providers/...` (versioned, the documented surface going
forward). The new version-chain endpoints have no legacy consumer; the
v1 path is the canonical address and the legacy alias on those routes
is incidental rather than load-bearing.

```
# New version-chain endpoints (v1 is canonical)
POST   /api/v1/providers/drafts                                  → 201 Draft
POST   /api/v1/providers/{id}/amend                              → 201 Draft
POST   /api/v1/providers/{id}/versions/{versionId}/activate      → 200 Active
POST   /api/v1/providers/{id}/versions/{versionId}/suspend       → 200 Suspended
POST   /api/v1/providers/{id}/versions/{versionId}/terminate     → 200 Terminated
POST   /api/v1/providers/{id}/reactivate                         → 200 Active
GET    /api/v1/providers/{id}/versions                           → page<Version>
GET    /api/v1/providers/{id}/versions/{versionId}               → Version

# Legacy endpoints (answer at both /api/Providers and /api/v1/providers)
GET    /api/v1/providers/{id}                                    → latest non-Draft version
POST   /api/v1/providers                                         → 201 (creates Draft + activates v1 in one shot)
PUT    /api/v1/providers/{id} against Active / non-Draft         → 409 Conflict
DELETE /api/v1/providers/{id}                                    → 204 (terminates head version)
```

The legacy `POST /api/Providers` path keeps its create-and-activate-v1
semantics so clients that don't need an explicit draft → activate flow
don't have to migrate. The legacy `PUT` path now surfaces 409 once a
provider has an Active version — callers must amend through the new
flow. The legacy `DELETE` path now performs a `Terminate` transition
on the head Active version, preserving history.

## Caveats / follow-ups

- **Bus fan-out.** Decorator over `IProviderVersionEventPublisher` not
  yet wired.
- **Cross-tenant draft isolation.** Drafts are partitioned by
  `TenantId` like every other row; no extra access control beyond the
  tenant middleware is implemented in this PR.
- **Network-participation deltas.** The v2 / Active row carries the
  full `NetworkParticipations` array; downstream consumers that diff
  participations across versions can subtract by `(planId,
  effectiveDate)` keys. A dedicated participation-delta event is
  reserved for a follow-up if the downstream cost of replaying full
  arrays becomes problematic.
- **`ProviderVerificationOrchestrator` integration.** Verification
  results write `IntegrityScore` / `IntegrityRating` /
  `LastVerifiedAt` / `NextVerificationDue` directly on the Active
  version. Because Active rows are read-only at the controller
  boundary, the orchestrator must call repository methods rather than
  the public PUT endpoint. The repository's `ReplaceVersionRowAsync`
  is the existing escape hatch for state-only mutations and remains
  available for orchestrator-style writes; a follow-up will introduce
  a dedicated `UpdateVerificationFieldsAsync` carve-out so the rest of
  the row stays immutable.
