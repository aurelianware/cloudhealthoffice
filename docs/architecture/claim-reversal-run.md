# Claim Reversal Run (Capability 5.12b)

## What this capability ships

5.12b ships the **payment-service `ReversalRunService`** — the
X12 mechanics layer of the 5.12 split. 5.12a established the
chain semantics + cross-service supersession (predecessor
superseded, new version persisted, `ClaimAdjustment` aggregate
in `AwaitingReadjudication` → `PendingReversal`); 5.12b ships the
operator-initiated batch that:

1. **Wires the orchestrator-finalize callback** (Premise A) —
   `ClaimAdjustmentService.OnNewVersionFinalizedAsync` is invoked
   from `ClaimAdjudicationOrchestrator` when a new claim version
   reaches a terminal pipeline outcome (Pass/Deny → `PendingReversal`,
   Reject → `Failed`, Pend → no-op). Without this wiring, no
   adjustment ever reaches `PendingReversal`; 5.12a's docstring
   at `ClaimAdjustmentService.cs:21–25` explicitly attributed
   this transition to the 5.12b orchestrator-callback path.

2. **Emits a batched 835 reversal envelope** per trading partner
   for the materialized `PendingReversal` adjustments. Reversal
   envelopes are produced by the existing
   `IBatchEraGeneratorService` (5.10); reversal-mode signaling
   threads through `EraPaymentInput.IsReversal` to
   `EraEnvelopeRecord.ReversalRunId`.

3. **Calls `POST /api/claims/{id}/void`** on claims-service per
   adjustment in the batch, transitioning the predecessor claim
   to `ClaimStatus.Voided`. The void endpoint exposes the 5.12a
   `ClaimFinalizationService.VoidAsync` service method (which was
   wired in 5.12a but had no HTTP surface until 5.12b).

4. **Wires the reversal-completion callback** (Premise E) —
   `ClaimFinalizationService.VoidAsync` invokes
   `ClaimAdjustmentService.MarkActiveOnReversalAsync` when the
   void carries a `ReversalRunId` correlation, transitioning the
   matching `PendingReversal` adjustment to `Active`.

After 5.12b ships, the full adjustment workflow is end-to-end
operational: an authorized operator submits a corrected claim →
new version goes through pipeline → adjustment lands in
`PendingReversal` → operator runs `ReversalRun` → reversal 835
emitted + predecessor voided + adjustment lands in `Active`.

## What this capability does NOT do

Pulled forward from the 5.12 plan-phase exclusions:

- **No 837 inbound parser.** Reversal triggers are operator-
  initiated only (Decision 2 from 5.12 plan; Phase 2 may add
  programmatic triggers).
- **No multi-envelope-per-file mode.** Same as 5.10 — Phase 1
  emits one ST/SE envelope per ISA/IEA file.
- **No sFTP / Availity transmission.** ReversalRun produces the
  EDI string + persists `EraEnvelopeRecord`; transmission is a
  separate Phase 2 capability.
- **No adjustment-of-adjustment.** Phase 1 caps chain depth at 1
  (5.12a Decision 11).
- **No `MapReversalAdjustments` / "reversal CARC code".** Per
  Plan-First Premise D, X12 005010X221A1 has no reversal CARC.
  The reversal signal is the CLP02 status code "22" set on
  `ClaimPayment.ClaimStatusCode`. CAS segments mirror the
  predecessor's adjustments with sign-flipped amounts; group
  codes (CO/PR/OA/PI) and reason codes are preserved verbatim.
- **No typed `ClaimsServiceClient` class.** Per Plan-First
  Premise B, ReversalRunService matches the existing
  `PaymentRunService` empirical pattern of inline named
  `HttpClient("ClaimsService")` calls (no typed wrapper).
  Introducing one would refactor across services in a feature
  PR (against modernization-PR discipline) — deferred to a
  cross-PR follow-up.

| `POST /api/reversalruns/execute` | Create + execute in one call. |
| `POST /api/reversalruns/{id}/execute` | Execute an existing `Pending` run. |

| `GET /api/reversalruns?from=…&to=…` | List runs within a date window. |

Pattern parity with `PaymentRunsController` — routes under
`/api/[controller]` without the `/v1` prefix (Plan-First
Premise F).

### claims-service

| Endpoint | Behavior |
|---|---|
| `POST /api/claims/{id}/void` | Voids a `Paid`/`PartiallyPaid`/`Adjusted` claim. Idempotent: `AlreadyVoided` returns 200. Body: `{ "reason": string, "reversalRunId": string? }`. The optional `reversalRunId` correlates the void to the originating `ReversalRun` and triggers the adjustment-lifecycle transition (`PendingReversal → Active`). |

## Reversal `Payment` construction

`ReversalRunService.BuildReversalPaymentAsync` builds one
`Payment` per adjustment from the predecessor's
`AdjudicationResult`. The construction pattern is the canonical
sign-flip mirror; no separate `MapReversalAdjustments` method.

```
predecessor                    reversal Payment
─────────────                  ──────────────────────────────
ApprovedAmount = 800m       →  TotalPaymentAmount = -800m
                            →  IsReversal = true
                            →  CheckNumber = "R-<8hex>"
                            →  PaymentDate = run.ExecutionStartedAt

ClaimPayment[0]                ClaimPayment[0]
─────────────                  ──────────────────────────────
ClaimStatusCode = "1" (paid)→  ClaimStatusCode = "22" (Reversal of Previous Payment)
PaymentAmount = 800m        →  PaymentAmount = -800m
PatientResp = 200m          →  PatientResp = -200m

ClaimAdjustments               ClaimAdjustments
───────────────                ──────────────────────────────
[0] PR/1/200m  "Deductible" →  [0] PR/1/-200m  "Deductible"
                                (group + reason preserved;
                                 amount sign-flipped)

ServiceLines[0]                ServiceLines[0]
───────────────                ──────────────────────────────
PaymentAmount = 800m        →  PaymentAmount = -800m
                                (per-line CAS data not
                                 carried — claim-level CAS
                                 is sufficient for Phase 1
                                 reversal envelopes; line CAS
                                 is a Phase 2 enhancement)
```

The X12 generator (`BatchEraGeneratorService`) emits whatever's
in the `ClaimPayment` — it does NOT branch on reversal mode
beyond threading `IsReversal` to `EraEnvelope.IsReversal` for
caller-side persistence. CLP02 = "22" comes from
`ClaimStatusCode`; sign-flipped amounts come from
`PaymentAmount` / `CAS.Amount`. The BPR01 segment naturally
emits "I" (Informational) for negative `TotalPaymentAmount` per
the existing `BatchEraGeneratorService.cs:176` branch.

## Lifecycle wiring (the load-bearing 5.12b additions)

### `AwaitingReadjudication → PendingReversal` (orchestrator-finalize callback)

```
ClaimAdjudicationOrchestrator
   .EmitAdjudicatedEventAsync(context)
       │
       ├─ PublishVersionAdjudicatedAsync (Mongo audit chain)
       ├─ MessageBus.SendAsync("claim-version-events", Adjudicated)
       └─ ClaimAdjustmentService.OnNewVersionFinalizedAsync(
              tenantId, context.Claim.Id, finalOutcome, ct)
                      │
                      ▼
          GetByNewClaimIdAsync(tenantId, newClaimId)
              │
              ├─ no match (fresh submission) → no-op
              │
              ├─ Status != AwaitingReadjudication
              │   (idempotent re-invocation) → no-op
              │
              └─ Status == AwaitingReadjudication
                      │
                      ├─ outcome=Pass / Deny → PendingReversal
                      ├─ outcome=Reject     → Failed
                      └─ outcome=Pend       → no transition
```

Failure of the callback is non-blocking: the adjudication has
already persisted; a follow-up sweep / operator intervention
can re-drive the lifecycle transition without losing the
pipeline outcome.

### `PendingReversal → Active` (void-success callback)

```
ClaimFinalizationService.VoidAsync(claimId, ClaimVoidRequest{ReversalRunId})
   │
   ├─ source-state validation (Paid / PartiallyPaid / Adjusted)
   ├─ MarkVoidedProjectionAsync (projection bypass)
   ├─ PublishVersionVoidedAsync (Mongo audit chain)
   ├─ PublishClaimFinalizedAsync (Kafka — Voided→"Reversed" mapper)
   │
   └─ if request.ReversalRunId is non-null:
         ClaimAdjustmentService.MarkActiveOnReversalAsync(
             tenantId, claim.Id, reversalRunId, ct)
                  │
                  ▼
       GetByPredecessorAndStatusAsync(tenantId, predId, PendingReversal)
              │
              ├─ no match (operator manual void) → no-op
              │
              └─ match → Active
                  │ persist ReversalRunId + ReversalCompletedAt
```

Operator-initiated voids without a `ReversalRunId` are no-ops
on the adjustment side (the void still persists + emits, just
doesn't drive the lifecycle transition).

## ReversalRun execution flow

```
1. Load ReversalRun by id; verify Status == Pending
2. Status → Running, persist
3. GET /api/v1/adjustments?status=PendingReversal&{criteria}
   (claims-service consumes ClaimAdjustmentListFilter shape;
    explicit-override path: criteria.AdjustmentIds list)
4. For each adjustment:
   a. GET /api/claims/{predecessorId} (load AdjudicationResult)
   b. Resolve trading partner via billing-provider NPI
      (cached; 5.10 ITradingPartnersClient)
   c. Build reversal Payment — sign-flip mirror; CLP02="22"
   d. Persist Payment; track id on run.PaymentIds
5. Group EraPaymentInput by TradingPartnerId
   (every input has IsReversal=true)
6. BatchEraGeneratorService.GenerateBatch(...)
   (CLP02="22" passes through verbatim from the ClaimStatusCode
    on the ClaimPayments; CAS segments emit sign-flipped
    amounts from cp.ClaimAdjustments)
7. For each EraEnvelope:
   - Create EraEnvelopeRecord with ReversalRunId set,
     PaymentRunId blank
   - Track id on run.EraEnvelopeIds
8. For each adjustment:
   - POST /api/claims/{predecessorId}/void
       body: { reason, reversalRunId }
   - 200 Voided / 200 AlreadyVoided → success
       (claims-service hook fires PendingReversal → Active)
   - 4xx / 5xx → warning appended; adjustment stays
       PendingReversal for retry/triage
9. Status → Completed
   (Failed only on hard exception; partial warnings still
    Completed per Decision 4 — partial-success preserves
    operational throughput)
10. Persist final state with execution duration
```

## Cross-service idempotency

| Surface | Idempotency key |
|---|---|
| `POST /api/reversalruns` | None — operator clicks "Run reversals". Future Phase: idempotency-header parity with PaymentRun. |
| `POST /api/reversalruns/{id}/execute` | Run-level `Status` guard (Pending → Running). Re-execute on Running/Completed → 400. |
| `POST /api/claims/{id}/void` | `AlreadyVoided` outcome → 200. The hook into `MarkActiveOnReversalAsync` fires only on the `Voided` outcome (not `AlreadyVoided`) so re-running a ReversalRun against a previously-completed batch doesn't double-update the adjustment. |
| Adjustment lifecycle callbacks | Both callbacks check the current `ClaimAdjustment.Status` before transitioning — re-invocation against a non-matching status is a logged no-op. |

## Failure modes & recovery

| Failure | Surface | Recovery |
|---|---|---|
| Trading-partner NPI doesn't resolve for a predecessor | `ReversalRun.Warnings` populated; envelope skipped for that adjustment | Operator fixes trading-partner config and re-runs (a fresh ReversalRun re-batches the still-`PendingReversal` adjustments) |
| Predecessor claim missing (404 on GET `/api/claims/{id}`) | Warning; adjustment skipped | Manual triage (orphaned adjustment row) |
| Void endpoint returns 422 (predecessor not in Voidable state — rare race with manual ops) | Warning; adjustment stays `PendingReversal` | Re-run after operator unblocks |
| Void endpoint returns 5xx | Warning; adjustment stays `PendingReversal` | Re-run after upstream recovery |
| Adjustment-lifecycle callback throws | Adjustment stays in source state; void already persisted | Phase 2 sweep job re-drives based on `ClaimVersionVoided` Mongo events |
| `BatchEraGeneratorService` mixed-mode batch (reversal + non-reversal in same partner group) | Envelope persists as PaymentRun (fail-closed default) | ReversalRunService never produces mixed batches; defensive |
| Orchestrator-callback throws inside `EmitAdjudicatedEventAsync` | Pipeline persisted; adjustment stays in `AwaitingReadjudication` | Phase 2 sweep job re-drives based on terminal `ClaimVersionAdjudicated` events |

## Capability boundary clarifications

### vs 5.10 (PaymentRun + Remittance Generation)

`PaymentRun` and `ReversalRun` share infrastructure:
- `IBatchEraGeneratorService` (1 service, 2 modes via
  `EraPaymentInput.IsReversal`)
- `IEraEnvelopeRepository` (1 storage, both `PaymentRunId` and
  `ReversalRunId` columns; exactly one populated per envelope)
- `Payment` (1 model, `IsReversal` flag distinguishes positive
  payment-run rows from negative reversal-run rows)
- `ICarcRarcMappingService` (unchanged — reversal envelopes
  re-use `MapClaimAdjustments` data with sign-flipped amounts;
  no new mapping methods)
- `ITradingPartnersClient` (unchanged)

5.10 paths preserved verbatim — `PaymentRunService` was not
touched in 5.12b.

### vs 5.12a (Adjustment Workflow Chain)

`ClaimAdjustmentService` was extended with two lifecycle
callbacks (`OnNewVersionFinalizedAsync`,
`MarkActiveOnReversalAsync`) but the existing
`CreateAdjustmentAsync` happy path was not touched. 5.12a's
test suite (extracted from `ClaimAdjustmentServiceTests`) still
passes verbatim; new lifecycle tests live in
`ClaimAdjustmentServiceLifecycleTests`.

`ClaimFinalizationService.VoidAsync` was extended with the
`ReversalRunId`-driven callback; the existing void-validation +
event-emission paths were not touched. 5.12a's
`ClaimFinalizationServiceVoidAsyncTests` still passes; the new
hook-firing tests live in `ClaimFinalizationServiceVoidReversalHookTests`.

### vs accumulator-service

5.12b doesn't directly emit to `accumulator-service` beyond what
5.12a already does. The void's Kafka emission via
`ClaimEventPublisher` translates `Voided → "Reversed"` (existing
mapping convention from before 5.12); the BP engine path is the
source of truth for accumulator un-application (5.12 Decision
16). 5.12b's batched 835 emission is observability/audit, not
the accumulator trigger.

### vs FHIR projection (5.11)

`ExplanationOfBenefitProjector` reads the latest claim version
unchanged. After 5.12b voids the predecessor, the EOB projection
shows `outcome="cancelled"` (existing 5.11 status mapping
handles this).

## Phase 2 follow-ups

- **Programmatic reversal triggers.** Today reversal is operator-
  initiated only (manual "Run reversals" button). Phase 2 may
  add policy-driven auto-reversal when an adjustment lands in
  `PendingReversal` and meets configured criteria.
- **Adjustment chain depth > 1.** Phase 1 caps depth at 1 via
  the `(TenantId, ClaimVersionId)` Mongo unique index; Phase 2
  widens the key with a generation field.
- **Per-adjustment retry granularity.** Phase 1 re-runs the
  whole batch on partial failure; Phase 2 may add per-adjustment
  retry IDs so a failed run doesn't re-process the successes.
- **Multi-envelope-per-file 835.** Same as 5.10 — Phase 2.
- **sFTP / Availity transmission.** Same as 5.10 — Phase 2.
- **Typed `ClaimsServiceClient` in payment-service.** Phase 2
  cross-PR refactor pulls inline `HttpClient("ClaimsService")`
  calls into a typed client wrapping both finalize + void +
  adjustment-list surfaces.
- **Lifecycle-callback sweep job.** Backstop for the rare race
  where the orchestrator-callback or void-callback throws after
  pipeline/void persisted; sweeps the Mongo
  `ClaimVersionAdjudicated` / `ClaimVersionVoided` events and
  re-drives any stuck adjustments.
